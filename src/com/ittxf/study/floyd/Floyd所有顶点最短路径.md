# Floyd 全源最短路径（三重循环很干净，但那份矩阵是有向的）

> 对应程序：[FloydAlgorithm.java](./FloydAlgorithm.java)（同文件里还有 `Graph`）
> 7 个顶点 A..G，`N = 65535`，对角线填 **0**。三重循环枚举中继点，一次算出**所有点对**的最短距离。
> 和 Dijkstra 那份对照着看最有意思：两份程序都叫 `Graph`、都用 65535、都 7 个顶点，
> 但**它们喂的是两张不同的图**（第六节实测）。

---

## 一、`main` 输出的形状

每个中继行打两行，7 组：

```
A A A F G B A
(A到A的最短距离为0) (A到B的最短距离为5) (A到C的最短距离为7) (A到D的最短距离为12) (A到E的最短距离为6) (A到F的最短距离为8) (A到G的最短距离为2)

G G E D F D F
(D到A的最短距离为12) (D到B的最短距离为9) ...

G G A F G G G
(G到A的最短距离为2) (G到B的最短距离为3) (G到C的最短距离为9) (G到D的最短距离为10) (G到E的最短距离为4) (G到F的最短距离为6) (G到G的最短距离为0)
```

第一行打的是 `vertex[pre[k][i]]` —— **前驱顶点的名字**，不是路径本身；第二行才是距离。
G 那一行 `[2, 3, 9, 10, 4, 6, 0]` 和 Dijkstra 从 G 跑出来的完全相同（这点下面还会用到）。

实测总账：**343 次 `len` 计算**（正好 `7³`），其中 **37 次真的改到了 `distance`**。
三重循环里没有"这轮选谁"的判断题，代码比 Dijkstra 短，但次数是它的 7 倍。

## 二、三重循环为什么这个顺序，以及 `pre[i][j] = pre[k][j]`

```java
for (int k = ...) for (int i = ...) for (int j = ...) {
    len = distance[i][k] + distance[k][j];
    if (len < distance[i][j]) { distance[i][j] = len; pre[i][j] = pre[k][j]; }
}
```

`k` 必须在最外层：**第 k 轮的含义是"只允许用前 k 个点当中继时，已经算好了所有点对"**。
`k` 挪到里层就不成立（会变成反复刷新，虽然距离最终也对，但推理不再是归纳式的）。

`pre[i][j] = pre[k][j]` 这句是最容易被写成 `i` 的地方。含义是：
`i → j` 的新路径既然要经过 `k`，那它"最后一段"该怎么走和 `k → j` 完全一样，所以把 `k` 那一行的前驱搬过来：

```
   i ───(前 k 个点当中继)───> k ───(沿用 k→j 已算好的走法)───> j
   所以 i→j 的前驱 = k→j 的前驱，而不是 k 本身，更不是 i
```

实测核对：用他的 `pre` 还原 **42 对**（去掉对角线）路径，逐段查原矩阵确认边存在、并把各段加起来和 `distance` 比：

```
   路径上有不存在的边：0 条
   路径长度 ≠ distance：0 条
   例：A→D 走 A B F D，distance = 12，逐段相加 = 5+3+4 = 12
   例：C→D 走 C E F D，distance = 17，逐段相加 = 8+5+4 = 17
```

## 三、对角线必须是 0

他的矩阵对角线填 0，这是 Floyd 的硬要求。把同一张图的对角线改成 65535 再跑，实测：

```
对角线 0  ：G 行 = [2, 3, 9, 10, 4, 6, 0]
对角线 N  ：G 行 = [2, 3, 9, 10, 4, 6, 4]     自己到自己 = 4
7 格不同：A→A (0 vs 4)  B→B (0 vs 6)  C→C (0 vs 14)  D→D (0 vs 8)  E→E (0 vs 8)  F→F (0 vs 8) ...
```

因为对角线的含义变成了"从 i 出发绕一圈回到 i 的最小代价"，不再是 0。
**这一处正好说明 Dijkstra 和 Floyd 的矩阵不能互换**：Dijkstra 那份对角线写 `N`（表示"没有自环"）完全无害，
喂给 Floyd 就把上面这 7 格改坏。

## 四、`this.distance = matrix` —— 没有拷贝

```java
public Graph(int length, char[] vertex, int[][] matrix) {
    this.vertex = vertex;
    this.distance = matrix;      // 直接拿引用
    this.pre = new int[length][length];
```

实测把传进去的那个数组打出来：

```
   调用前 caller[0] = [0, 5, 7, 65535, 65535, 65535, 2]
   floyd() 之后 caller[0] = [0, 5, 7, 12, 6, 8, 2]      ← 调用方自己的数组被就地改掉了
```

所以 `main` 里那个 `matrix` 在 `graph.floyd()` 之后已经**不再是邻接矩阵**，而是最终答案。
再调一次 `floyd()` 结果不变（已经是最短路，幂等 —— 实测 `[0,5,7,12,6,8,2]` 原样），
但这只是运气：如果想拿原图再算一遍，只能重新造一份矩阵。

对照仓库里另外两份：`PrimAlgorithm.createGraph()` 和 `KruskalCase.kruskalCase()` 都是**逐格拷进自己的数组**的，
所以 Prim 那份改不到调用方的 `adjMatrix`。**Floyd 这一份是唯一把输入直接接管的。**
（顺带这也让"距离表"省了一份内存 —— 但省得很便宜，因为 `pre` 还要一份 `V×V`。）

## 五、`INF` 千万别换成 `Integer.MAX_VALUE`

`len = distance[i][k] + distance[k][j]` 是两个 INF 相加。他的 `65535 + 65535 = 131,070` 在 `int` 里安全。
换成 `Integer.MAX_VALUE` 试试（两个孤立连通块 `{A-B}`、`{C-D}`，实测）：

```
INF = Integer.MAX_VALUE 跑完：
  [0, 1, -2147483647, -2147483647]
  [1, 0, -2147483648, -2147483648]
  [-2147483647, -2147483648, -12, -18]
  [-2147483647, -2147483648, -18, -24]

INF = 65535 跑同一张图：
  [0, 1, 65535, 65535]
  [1, 0, 65535, 65535]
  [65535, 65535, 0, 2]
  [65535, 65535, 2, 0]     ← 不连通就老老实实是 INF
```

`MAX_VALUE + MAX_VALUE` 溢出成 **-2**，比任何真实距离都小，于是 `if (len < distance[i][j])` 每次都成立，
**"不连通"被一路加成负数**，最后连 `C→D = 2` 这条真边都被盖成 `-12`、`-18`。
输出格式完全正常，全是负数。要安全就用 `Integer.MAX_VALUE / 2` 或者像他这样用一个远小于上限的常量。

## 六、它和 Dijkstra 那份不是同一张图（实测）

把两份矩阵逐格对比 `m[i][j]` vs `m[j][i]`：

```
   Dijkstra 那份：上三角 10 条边，完全对称，对角线 = 65535
   Floyd    那份：上三角 9 条边，6 处不对称，对角线 = 0
      B->D = 65535 而 D->B = 9
      B->F = 3      而 F->B = 65535
      B->G = 65535  而 G->B = 3
```

也就是说**凡是牵涉 B 的那几条边，只填了一半**：`D→B`、`G→B` 填了，反方向 `B→D`、`B→G` 空着；
而 `B→F = 3` 只有去程没有回程。Floyd 本身不要求对称（它对有向图照样正确），
所以这份代码"跑起来了、输出很漂亮"，只是它算的是一张**有向图**。

后果可以直接量出来 —— 拿对称那张图（Dijkstra 的矩阵，只把对角线改成 0）跑 Floyd，再和他这份的输出比：

```
   49 对里不同的：4 对，全部从 B 出发
      B→D  dij=9  floyd=7
      B→E  dij=7  floyd=8
      B→F  dij=9  floyd=3
      B→G  dij=3  floyd=7
   其余 6 个顶点出发的 42 对全部一致
```

而且这 4 对**两个方向都有**：`B→D` 7 < 9、`B→F` 3 < 9 变小（因为有向图里多了 `B→F` 这条捷径），
`B→E` 8 > 7、`B→G` 7 > 3 变大（因为 `B→G` 那条 3 的边丢了，只能绕 `B→F→G`）。
所以**不能靠"谁的数更小谁对"来发现这种录入错误**。最便宜的自查就两招：
把矩阵和自己的转置比一遍（不对称就是录入问题），或者拿 Floyd 的结果和"跑 V 次 Dijkstra"对一遍。

顺带给一句好消息：把 Floyd 的矩阵对角线改成 0、其余不动之后，**49 对与逐点跑 Dijkstra 完全一致（0 处不同）** ✓，
两个独立实现的算法互相印证这件事是成立的。

## 七、代价：`V³`，以及"要不要跑 V 次 Dijkstra"

实测同一批连通随机图（每张都用另一种实现核对过总距离）：

| V | 一次 Floyd | V 次 Dijkstra | Floyd 多占的内存（`pre` + 复用输入的 `distance`） |
| --- | --- | --- | --- |
| 200 | 11 ms | 19 ms | 320,000 字节（2 张 200×200） |
| 400 | 60 ms | 60 ms | 1,280,000 字节 |
| 600 | 62 ms | 185 ms | 2,880,000 字节 |
| 800 | 146 ms | 413 ms | 5,120,000 字节 |

（表里"Dijkstra"那一列是同一份朴素数组版实现，见 Dijkstra 笔记第七节。）

两列在 V=400 处打平，之后 Floyd 明显占优 —— 因为朴素 Dijkstra 每次也要 `V²`，跑 V 次就是 `V³` 且常数更大。
**稠密矩阵 + 要全源答案**，Floyd 是更省事的那个；反过来，只问单源就别用 Floyd（`V³` 全算完只为拿一行）。

`V=800` 那一档的绝对数字：**512,000,000 次 `len` 计算**，两张 `int[800][800]` = 5.1 MB。
Floyd 的内存下限就是两份 `V×V`（`distance` 和 `pre`），所以它不适合"顶点几万个、只要单源"的场景 —— 那正是堆版 Dijkstra 的地盘。

## 八、一句话记住

```
   k 必须在最外层；pre[i][j] = pre[k][j] 是"借 k→j 已经算好的走法"，42 对路径实测全部合法且加总等于 distance；
   对角线必须 0（换成 65535 会让 A→A 变成 4，7 格变怪数）；INF 换成 MAX_VALUE 会溢出不通，
   而且 65535+65535 本来就安全，他这个常量选得刚好；
   this.distance = matrix 不拷贝，跑完原矩阵就被改掉了（Prim/Kruskal 那两份是逐格拷的）；
   这份矩阵里 B 的三条边只填了一半（6 处不对称），所以它算的是一张有向图 ——
   从 B 出发的 4 对距离和对称矩阵上的 Dijkstra 不一致，其余 42 对完全一致。
```
