# Kruskal 最小生成树（`ends[i] = 0` 同时表示"根"和"没连"）

> 对应程序：[KruskalCase.java](./KruskalCase.java)（同一文件里还有 `EData`）
> 7 个顶点 A..G、12 条边。思路：把所有边按权值排序，从小到大依次尝试，
> 两个端点已经在同一棵树里就丢掉（会成环），否则收下并合并两棵树。
> **注意这张图和 Prim 笔记里那张不是同一张图**：这里 12 条边、`INF = Integer.MAX_VALUE`；
> Prim 那份 10 条边、用 `10000` 表示无边。所以 36 和 25 两个总权值之间没有任何可比性。

```

                    <E,G>=8, <F,G>=9, <B,C>=10, <A,B>=12, <A,G>=14, <A,F>=16]
顶点数组=[A, B, C, D, E, F, G]

EData{<E, F> weight=2}

```

12 条边里收下 6 条（= V-1 ✓），丢掉 6 条：`<C,E>=5`、`<C,F>=6`、`<F,G>=9`、`<B,C>=10`、`<A,G>=14`、`<A,F>=16`。
6 条边的权值加起来是 **36**（程序自己不打总数，这是把上面 6 行加起来的）。

拿一份独立实现（同样的边表、同样的排序，但并查集用 `parent[i] = -1` 表示"自己是根"）核对：
**总权值 36，一致** ✓。另外在 V=100..600 的 6 张随机连通图上跑，两边给出的总权值次次相同（见第六节表）。

## 二、`ends` 数组到底是什么

`ends[i]` 记的是"顶点 i 所在那棵树，往下走到的终点是哪个"，`0` 表示**没有记录**（也就是 i 自己就是根）。
最后那一行 `[6, 5, 3, 5, 5, 6, 0]` 翻译出来：

```
A(0) → 6 → ends[6] = 0，所以 A 这一支的根是 G
B(1) → 5 → 6 → 根 G
C(2) → 3 → 5 → 6 → 根 G
D(3) → 5 → 6 → 根 G
E(4) → 5 → 6 → 根 G
F(5) → 6 → 根 G
G(6) → 0 → 自己就是根
```

七个点全部走到 G，说明最后合成了一棵树 ✓。`getVertexEnd(ends, i)` 就是顺着这条链一路走到第一个 `ends[i] == 0` 的点。

判环因此只需比较两个端点各自的"终点"：`m != n` 就是两棵不同的树，可以连。
每次连边做的是 `ends[m] = n`（把 m 那棵挂到 n 那棵的根上）。

---

## 三、`ends[i] = 0` 一身两用，是这个实现里最脆的一处

`0` 同时是"没连过"和"我就是根"两个意思，而 A 的下标恰好是 0。
也就是说 **A 这一棵树的根和"空"长得一模一样**。它会不会出事，取决于有没有可能把 `ends[m] = 0` 写下去：

```java
int m = getVertexEnd(ends, p1);
int n = getVertexEnd(ends, p2);
if (m != n) ends[m] = n;      // n 万一等于 0，这句就是空操作
```

`getVertexEnd` 的循环是 `while (ends[i] != 0) i = ends[i];` —— 只要起点不是 0，`i` 永远只会跳到非 0 的值上，
**所以返回值等于 0 的唯一可能是"传进来的 p2 本身就是 0"**。
而 `getEdges()` 造边时写的是 `for (i = 0..n) for (j = i+1..n)`，边的第二个端点下标 `j` 恒 ≥ 1。
**结论：他这份程序里 `n` 永远不可能是 0，这个隐患碰不到。** 但它完全是靠"边恰好按下标升序生成"撑住的。

把这个前提拿掉（把同一条边写成 `<C,A>` 而不是 `<A,C>`），立刻露馅。
同一个三角形 `{B-C:1, A-C:2, A-B:3}`，把三条边的方向写成 `<B,C>`、`<C,A>`、`<A,B>` 依次喂进同一份逻辑，实测：

```
正常顺序（<B,C>,<A,C>,<A,B>，也就是 getEdges 会生成的形状）：
   ends=[2, 2, 0] 接受 2 条（应 2 条）总权 = 3        ← 与真实最小生成树 3 一致
写成 <B,C>,<C,A>,<A,B>：
   处理 <B,C>：ends[1] = 2
   处理 <C,A>：m=2, n=0 → ends[2] = 0（等于没改！）
   处理 <A,B>：m=0, n=2 → 两个终点不同 → 收下 → 第三条边也进了树，3 个点 3 条边 = 成环
   → java.lang.ArrayIndexOutOfBoundsException: Index 2 out of bounds for length 2
```

**成环之后不是给出一个偏大的答案，而是直接崩**：`res` 数组是按 `vertexArr.length - 1` 开的，
接受到第 V 条边时 `res[index++]` 就越界了。
这一点值得记住：**用 `ends[m] = 0` 这种"哨兵值恰好也是合法数据"的写法，
出问题时不会给错数字，而是把整个程序掀翻。**

## 四、图不连通：结果数组里留下 `null`，程序照样打印

`res` 固定开 `V-1` 格，但只填 `index` 格。构造一张 D 孤立的图（只有 A-B、A-C 两条边），
把同一份 `kruskal()` 逻辑跑上去，实测：

```
ends=[1, 2, 0, 0] 接受 2 条（应 3 条）null 槽 = 1 总权 = 4
```

而打印那段是

```java
for (EData re : res) { System.out.println(re); }
```

增强 for 会**把剩下的空槽原样遍历出来**，`System.out.println(一个 null 引用)` 打出的就是字面量 `null`。
所以不连通时的现象是：最小生成树那一段少一行、多一行 `null`，前面所有输出完全正常。
（对照 Prim 那份：同样这张图，Prim 打印的是 `<A, C> 权值：10000` 这种假边，见 Prim 笔记第四节。
两份实现对"图不连通"的反应一个是打 `null`、一个是编数字，都不报错。）

顺带：`while (ends[i] != 0) i = ends[i];` 如果两端被写成互相指向会死循环，但这里 `n` 取的时候必然是根
（`ends[n] == 0`），所以 `ends[m] = n` 不会造出环 —— 这个死循环在正常输入下走不到。

## 五、`compareTo` 用减法，以及两处和代码不一致的注释

```java
public int compareTo(EData o) { return this.weight - o.weight; }
```

减法比较器是经典隐患：差值超出 `int` 范围就溢出，符号反过来，排序结果错。纯算式实测：

```
2000000000 - (-2000000000) 作为 int = -294967296   （真实差 4,000,000,000，溢出成负数）
用减法比较器排 [2000000000, -2000000000, 5] -> [2000000000, -2000000000, 5]   ← 没排
用 Integer.compare 排                      -> [-2000000000, 5, 2000000000]  ← 正确
```

**但在这一份程序里触发不到**：`getEdges()` 已经把 `INF`（`Integer.MAX_VALUE`）过滤掉了，
剩下的权值都在 2..16 之间。要触发得让边权大到接近 `Integer.MAX_VALUE` ——
而那时它和 `INF` 本身就会撞车（`matrix[i][j] != INF` 这一句判断的是**相等**，
所以任何一条真的等于 `Integer.MAX_VALUE` 的边会被当成"无边"，比 Prim 那个 10000 更隐蔽）。

两处注释和代码不一致（不影响运行，但读代码时会误导）：

- `printMatrix()` 里注释写"遇到 **10000** 就打印无穷大符号"，实际判断的是 `matrix[i][j] == INF`（`Integer.MAX_VALUE`）。
  这句注释是从 Prim 那份复制过来的，那边的确用 10000。
- 同一处注释写"普通数字，占 6 个宽度右对齐"，代码是 `%5d`；`∞` 用的是 `%5s`。

## 六、代价：排序 + 线性找下标 + 走链

`kruskal()` 里三处开销：

| 位置 | 做的事 | 量级 |
| --- | --- | --- |
| `getEdges()` | 扫上三角 `V²/2` 格，生成 `E` 条边 | O(V²)，**无论图多稀疏都先扫一遍矩阵** |
| `sortEdges()` | `Collections.sort`（TimSort） | O(E log E) |
| 主循环里的 `getVertexIndex()` | 在 `vertexArr` 里**线性查**顶点下标，每条边查 2 次 | O(V) × 2E → O(E·V) |
| 主循环里的 `getVertexEnd()` | 顺 `ends` 链走到根 | 无路径压缩、无按秩合并，最坏 O(V) |

实测（连通随机图，每张都拿第一节的参考实现核对总权值）：

| V | E | 取边+排序 | 本程序主循环 | 本程序 Prim | 与参考一致 |
| --- | --- | --- | --- | --- | --- |
| 100 | 387 | 0 ms | 0 ms | 2 ms | 是 |
| 200 | 785 | 0 ms | 0 ms | 6 ms | 是 |
| 400 | 1,585 | 1 ms | 0 ms | 13 ms | 是 |
| 600 | 2,385 | 0 ms | 0 ms | **45 ms** | 是 |

V=600、E=2,385 时主循环依然是 0 ms —— `getVertexIndex` 的线性扫描（600 次比较 × 2 × 2385 条边 ≈ 290 万次）
在这个量级上还远不到看的地方，而 Prim 那份的 `V³` 已经要 45 ms。
**所以"Kruskal 慢在 `getVertexIndex`"这件事理论成立、实测看不见**；真要让它们较量，得把 V 拉到几千。

排序那一步之所以看着是 0 ms，是因为 `getEdges()`+`sort` 在 2,385 条边上就是几百微秒级别的活。

## 七、`kruskalCase()` 这个方法名

初始化用的那个方法叫 `kruskalCase(char[] vertex, int[][] matrix)`，和类名同名但**不是构造器**（没有返回类型才是构造器，
它写了 `private void`，所以是个普通方法）。真正的构造器是无参默认的那个。
这不影响结果，但很容易读成"构造器"，从而误以为 `new KruskalCase()` 就已经把图建好了 ——
实际上少了 `kruskalCase(vertex, matrix)` 这一句，`vertexArr` 会是 `null`，`getEdges()` 直接 NPE。

## 八、一句话记住

```
   排序后逐条试边、用 ends[] 走链判环，这份实现在他这张图上给出 36，和独立实现一致（V 到 600 的随机图也一致）；
   ends[i]=0 一身两用，全靠"边恒为 i<j、第二个端点下标不可能为 0"才没出事 ——
   把边写成 <C,A> 再喂进去，成环时不是给错数字而是 ArrayIndexOutOfBoundsException（res 只开了 V-1 格）；
   图不连通时 res 剩下的空槽会被增强 for 打成字面量 null；
   INF 用相等判断，所以一条真的等于 Integer.MAX_VALUE 的边会被当成不存在；
   它和 Prim 那份用的是两张不同的图（12 条边 vs 10 条边），36 和 25 不可比。
```
