# 汉诺塔（分治：只管最外面那一层，剩下的交给递归）

> 对应程序：[HanoiTower.java](./HanoiTower.java)
> 规则：三根柱子 A/B/C，n 个大小不同的盘子初始全部叠在 A 上（小的在上），要求全部搬到 C，
> 一次只能搬一个盘，且**任何时刻大盘不能压在小盘上**。B 是中转柱。

---

## 一、分治在这道题里分的是什么

手写 3 个盘的步骤不难，难的是 n 个盘。分治的切入点是一句很"赖皮"的话：

```
   要搬走 A 上 n 个盘，等价于三件事：
       ① 先把上面 n-1 个盘从 A 挪开（挪到 B，因为 C 要留给最大的那个盘）
       ② 此时 A 底部那个最大的盘上面已经空了，直接 A -> C
       ③ 再把刚才挪走的 n-1 个盘从 B 搬到 C（借助 A）
   ①③ 这两件事本身就是"汉诺塔问题"，规模小一层，所以直接调用自己。
```

代码里就三行：

```java
hanoiTower(n - 1, a, c, b);                            // ①
System.out.println("第" + n + "个盘从" + a + "->" + c); // ②
hanoiTower(n - 1, b, a, c);                            // ③
```

**关键是把形参 `(n, a, b, c)` 读成一句自然语言：「把 n 个盘从 a 搬到 c，中途可以借用 b」。**
中间那根柱子永远是"可借用"的那根，所以它排在第二个位置，`c` 才是目的地。
①里目的地是 B、可借用的是 C，所以写 `(n-1, a, c, b)`；③里源柱变成 B、目的地还是 C、可借用的是 A，
所以写 `(n-1, b, a, c)`。两次调用的参数不是随便打乱的，是**同一句话换了角色**。

## 二、`hanoiTower(5, 'A', 'B', 'C')` 实际打印了什么

直接跑（JDK 21，`java -Dstdout.encoding=UTF-8`），共 **31 行**，首尾各三行是：

```
第1个盘从A->C
第2个盘从A->B
第1个盘从C->B
... （中间 25 行）
第1个盘从B->A
第2个盘从B->C
第1个盘从A->C
```

把 n 改成 3，配合一个"真棋盘"模拟器（每步真的把柱顶的盘子 pop 出来 push 到另一根柱子），
可以把状态摊开看（方括号**左边是柱顶**）：

```
第1个盘从A->C | A:[2, 3] B:[]     C:[1]
第2个盘从A->B | A:[3]    B:[2]    C:[1]
第1个盘从C->B | A:[3]    B:[1, 2] C:[]
第3个盘从A->C | A:[]     B:[1, 2] C:[3]
第1个盘从B->A | A:[1]    B:[2]    C:[3]
第2个盘从B->C | A:[1]    B:[]     C:[2, 3]
第1个盘从A->C | A:[]     B:[]     C:[1, 2, 3]
```

第四行就是"②搬最大盘"那一刻：A 上只剩 `[3]`，B 上正好收着上面那两层 `[1, 2]`。
①的递归结束后棋盘一定是这个形状 —— 这就是分治那三句话的可视化。

模拟器同时检查了三件事，n=1..12 全部通过：

| n | 打印次数 | 大盘压小盘 | 从空柱取盘 | 最终 C 柱是 1..n 且 A/B 空 |
| --- | --- | --- | --- | --- |
| 1 | 1 | 0 | 0 | 是 |
| 3 | 7 | 0 | 0 | 是 |
| 5 | 31 | 0 | 0 | 是 |
| 8 | 255 | 0 | 0 | 是 |
| 12 | 4,095 | 0 | 0 | 是 |

顺带确认了编号约定：**"第 1 个盘"是最小、最上面那个，"第 n 个盘"是最大、压在底部的**。
因为模拟器里每次 pop 出的盘号和打印的盘号逐一比对，一次都没对不上。

## 三、步数是 2^n - 1，而且"调用次数"也刚好等于它

实测（把打印换成计数器，n 从 1 跑到 25）：

| n | 打印次数 | 2^n-1 | 方法被调用次数 | 最大递归深度 |
| --- | --- | --- | --- | --- |
| 1 | 1 | 1 | 1 | 1 |
| 3 | 7 | 7 | 7 | 3 |
| 5 | 31 | 31 | 31 | 5 |
| 10 | 1,023 | 1,023 | 1,023 | 10 |
| 20 | 1,048,575 | 1,048,575 | 1,048,575 | 20 |
| 25 | 33,554,431 | 33,554,431 | 33,554,431 | 25 |

两个数字一样不是巧合，是这份代码的结构决定的：

```
   每次进入方法，要么走 n == 1 分支打印一次，要么走 else 分支打印一次（中间那行 println）
   —— 一次调用恰好对应一次打印，所以 调用次数 = 打印次数 = 2^n - 1

   而两者都满足同一个递推：T(n) = 2*T(n-1) + 1, T(1) = 1  =>  T(n) = 2^n - 1
```

**最大递归深度恰好等于 n**（表里那一列就是 n），这一点很反直觉：打印量指数级爆炸，
但栈最深只有 n 层。所以汉诺塔的瓶颈从来不是爆栈，是时间。

## 四、代价在哪：n 每加 1，时间翻一倍

只计数、不打印（避免 IO 干扰），实测耗时：

| n | 打印次数 | 耗时 |
| --- | --- | --- |
| 24 | 16,777,215 | 16 ms |
| 26 | 67,108,863 | 62 ms |
| 28 | 268,435,455 | 259 ms |
| 30 | 1,073,741,823 | 1,026 ms |
| 32 | 4,294,967,295 | 4,090 ms |
| 34 | 17,179,869,183 | 16,390 ms |

n 从 24 → 34，盘数没变、代码没变，只把 n 加 10，时间从 16ms 变成 16.4s —— **正好 1024 倍 = 2^10**。
n=34 那一档跑出 17,179,869,183 次调用只花 16.4 秒，约 10 亿次/秒；这说明慢不是 JVM 慢，
是**算法本身要求这么多步**。任何"再优化一下递归"的尝试都没用：2^n - 1 是这道题的最优解，
不是这份实现的缺陷。

另一个实测数字：**打印比递归本身贵得多**。把 `System.out.println` 换回真正的打印
（输出重定向到空设备），

| n | 行数 | 墙钟时间 |
| --- | --- | --- |
| 5 | 31 | 10 ms（几乎全是 JVM 启动） |
| 15 | 32,767 | 44 ms |
| 20 | 1,048,575 | 412 ms |
| 22 | 4,194,303 | 1,463 ms |

n=22 是 419 万行 / 1.46 秒 ≈ **每秒 290 万行**；而同一规模的纯计数能跑到每秒 10 亿次。
也就是说这份代码里 99.9% 的时间花在"把字打到控制台"上，真正的递归只占千分之一。
`main` 里把 5 改成 25 就等着看半小时吧 —— 33,554,431 行打印要按这个速度跑约 11 秒，
改成 30 就是 10 亿行、6 分钟起步。

## 五、两个 swap 写错的样子（都不报错，但结局完全不同）

递归最坑的地方是**写错了不报错，只是悄悄不做完**。用第二节那个真棋盘模拟器跑三种错法：

**错法一：第一次递归忘了交换，写成 `hanoiTower(n - 1, a, b, c)`**

| n | 打印次数 | 大盘压小盘 | 从空柱取盘 | 结局 |
| --- | --- | --- | --- | --- |
| 3 | 7 | 2 | 4 | 未完成 |
| 5 | 31 | 6 | 26 | 未完成 |
| 8 | 255 | 7 | 247 | 未完成 |

n=8 时 255 次打印里有 247 次是"伸手去一根空柱子上拿盘子"，也就是整个移动过程基本是虚构的；
最后 C 柱从上到下是 `[8, 7, 6, 5, 4, 3, 2, 1]` —— 最大的盘在顶上，完全反了。
程序一路正常打印，一个字都没提示出错。

**错法二：第三次递归写成 `hanoiTower(n - 1, b, c, a)`（把"借用柱"当成了目的地）**

| n | 打印次数 | 大盘压小盘 | 从空柱取盘 | 结局 |
| --- | --- | --- | --- | --- |
| 3 | 7 | 0 | 0 | 未完成，C 柱只有 `[3]` |
| 5 | 31 | 0 | 0 | 未完成，C 柱 `[2, 5]` |
| 8 | 255 | 0 | 0 | 未完成，C 柱 `[2, 5, 8]` |

**这才是最阴的一种**：每一步都是合法移动（从没违反"大盘不能压小盘"，也从没从空柱取盘），
打印出来的 255 行看着和正确答案一样头头是道，但盘子根本没搬完，散在三根柱子上。
想发现它只能靠"最后检查一遍棋盘"，光看输出格式是看不出来的。

**错法三：把 ② 那句 println 提到 ① 前面（先搬大盘）**

| n | 打印次数 | 大盘压小盘 | 打印的盘号其实不在柱顶 | 结局 |
| --- | --- | --- | --- | --- |
| 3 | 7 | 3 | 6 | 未完成 |
| 5 | 31 | 11 | 27 | 未完成 |
| 8 | 255 | 111 | 241 | 未完成 |

n=5 时 31 步里有 11 步把大盘压在了小盘上，且 27 次打印的盘号根本不是那根柱子的栈顶 ——
说明"第 n 个盘从 A->C"这句话在物理上压根做不到。这个错法最容易被肉眼发现，
因为它第一行就打印"第 5 个盘从 A->C"，而此时 A 顶上明明是 1 号盘。

## 六、`n == 1` 少写了半边：`hanoiTower(0, ...)` 直接爆栈

跳出条件写的是 `if (n == 1)`，不是 `if (n <= 1)`。于是 n=0 进来走的是 else 分支：

```
   hanoiTower(0) -> hanoiTower(-1) -> hanoiTower(-2) -> ...   永远不会等于 1
```

实测 `java.lang.StackOverflowError`，栈往下走了约 **19,988 层**才断。
把参数改成从控制台/配置文件读进来（`Integer.parseInt` 读到 0 或负数）时，
这不是"什么都不打印"，而是当场抛栈 —— 而且抛出的是最深 2 万层的 `StackOverflowError`，
打印出来糊满整个屏幕。要么把条件写成 `n <= 1` 并让它静默返回，要么在入口处挡掉 `n < 1`。

（顺带说清：n=1 是正常打印一行 `第1个盘从A->C`；这份代码对 n=0 没有任何保护。）

## 七、64 个盘的传说，用这份代码的账算一遍

```
2^64 - 1 = 18,446,744,073,709,551,615 步
```

- 一秒搬一个：`2^64-1` 秒 ≈ **5849 亿年**。
- 一秒搬一亿个（比第四节实测的每秒 10 亿次还慢一档）：**5849.42 年**。

传说里"僧侣搬完 64 个盘子世界就毁灭"的量化版本就是这么来的。
而这份 `main` 里的数字是 5 —— 31 步，一秒内打印完。

## 八、一句话记住

```
   形参读成「把 n 个盘从 a 搬到 c，可借 b」，三次调用只是同一句话换角色；
   打印次数 = 调用次数 = 2^n - 1，递归深度只有 n，所以慢在步数不在栈；
   递归写错不报错，只会静默搬不完 —— 想验证就只能拿棋盘再走一遍。
```
