# 贪婪算法 · 电台选台（结果取决于 HashSet 的心情）

> 对应程序：[GreedyAlgorithm.java](./GreedyAlgorithm.java)
> 5 个电台覆盖 8 个地区，要求用最少的电台覆盖全部地区。
> 贪心策略：每一轮挑"**还能覆盖最多的未覆盖地区**"的那个电台，把它的地区从 `allAreas` 里删掉，直到没有剩余。

---

## 一、`main` 跑出来的结果

```
广播电台的集合：{K1=[上海, 天津, 北京], K2=[广州, 北京, 深圳], K3=[成都, 上海, 杭州], K4=[上海, 天津], K5=[大连, 杭州]}
所有地区：[成都, 上海, 广州, 天津, 大连, 杭州, 北京, 深圳]
得到的选择结果是：[K1, K2, K3, K5]
```

按"每轮选最大"走一遍（实测逐轮记录）：

| 轮 | 各电台还能覆盖多少**未覆盖**地区（按 K1→K5 顺序看） | 选中 |
| --- | --- | --- |
| 1 | K1 3、K2 3、K3 3、K4 2、K5 2 | **K1**（第一个达到 3 的，后面两个 3 被严格 `<` 挡住） |
| 2 | K1 0、K2 2（广州、深圳）、K3 2（成都、杭州）、K4 0、K5 2 | **K2**（又是第一个达到 2 的） |
| 3 | K3 2（成都、杭州）、K5 2（杭州、大连），K1/K2/K4 都是 0 | **K3** |
| 4 | 只剩大连，只有 K5 覆盖 | **K5** |

一共 4 轮，选了 4 个电台，`allAreas` 清空。

**这个答案是对的，而且是"刚刚好"对的**：把 5 个电台的全部 32 个子集穷举一遍（实测）——

```
size 1 -> 0 个可行覆盖
size 2 -> 0 个
size 3 -> 0 个
size 4 -> 2 个：[K1, K2, K3, K5]  和  [K2, K3, K4, K5]
```

最少要 4 个电台，而**能覆盖全部 8 个地区的 4 电台组合只有这两种**，程序恰好命中了第一种。
（硬约束很清楚：大连只有 K5 覆盖、成都只有 K3 覆盖、广州和深圳只有 K2 覆盖，
这三个定了以后只剩"北京、上海、天津"，K1 或 K4 二选一 —— 所以是 4 个，且只有两种解。）

## 二、真正值得记住的一处：`maxCount < tempSet.size()` 是**严格小于**

比较写成 `if (tempSet.size() > 0 && (maxCount < tempSet.size()))`，
平局时**不更新** `maxKey`，所以胜者是"**遍历顺序里第一个**达到最大值的电台"。

第 1 轮里 K1、K2、K3 都能覆盖 3 个未覆盖地区，程序挑了 K1 —— 而 K1 之所以赢，
只是因为 `broadcasts.keySet()` 恰好把 K1 排在第一个。这不是逻辑，是容器的实现细节。

实测：同一份数据（5 个电台、覆盖关系一模一样），只换容器的构造方式——

| `broadcasts` 怎么建的 | key 遍历顺序 | 选中顺序 | 最终 `selects` |
| --- | --- | --- | --- |
| `new HashMap<>()` + 依次 put 5 个（程序里的写法） | `[K1, K2, K3, K4, K5]` | K1→K2→K3→K5 | `[K1, K2, K3, K5]` |
| `new HashMap<>()` + `putAll(...)` | `[K3, K4, K5, K1, K2]` | K3→K2→K4→K5 | **`[K2, K3, K4, K5]`** |
| `TreeMap` | `[K1, K2, K3, K4, K5]` | K1→K2→K3→K5 | `[K1, K2, K3, K5]` |
| `LinkedHashMap`（按 K1..K5 插入） | `[K1, K2, K3, K4, K5]` | K1→K2→K3→K5 | `[K1, K2, K3, K5]` |

**同一份数据、同一个算法，跑出两种答案。**差别只在第二行那种构造方式：
`HashMap.putAll()` 会按 `size/0.75 + 1` 预先把表扩容到 8 格，而逐个 `put` 的表是默认的 16 格 ——
桶数不同，`keySet()` 的遍历顺序就不同。按 `[K3, K4, K5, K1, K2]` 这个顺序走一遍实测是
K3(3) → K2(2) → K4(1) → K5(1)：第 1 轮 K3 抢在 K1/K2 前面拿到 3，
第 3 轮未覆盖的只剩"天津、大连"，K4 和 K5 各能补 1 个，而 K4 排在 K5 前面 ——
于是 K1 全程没轮到，最后的解里是 K4 顶上了它的位置。

而 **K4 是被 K1 支配的**（`{上海,天津}` ⊊ `{北京,上海,天津}`）：任何用了 K4 的方案，把 K4 换成 K1 都不会变差，
所以最优解里本不该有 K4 的位置。它被选中却仍然得到 4 个电台，纯属运气 ——
**K1 多出来的那个"北京"恰好已经被 K2 覆盖了**，于是这个"吃亏"的选择没有暴露出来。
换一组数据（北京不被任何其他电台覆盖），同样的遍历顺序就会多花一个电台。

**教训：只要贪心里写了"取最大"，就必须明确平局怎么处理，否则答案由哈希决定。**
稳定的写法是把 `maxCount < tempSet.size()` 改成带二级比较（例如再比 key 的字典序），或者干脆用 `TreeMap`/`LinkedHashMap` 把顺序钉死。

一个更极端的平局实验（两个电台覆盖完全相同）：

```
X={a,b} Y={a,b} Z={c,d}
按 X,Y,Z 遍历 -> 选 [X, Z]
按 Y,X,Z 遍历 -> 选 [Y, Z]      ← 只有"X 还是 Y"这一处不同，纯粹由顺序决定
```

## 三、`selects` 打印的顺序不是选中顺序

第 3 节表格最后一行：选中顺序是 `K3→K2→K4→K5`，打印出来却是 `[K2, K3, K4, K5]`。
因为 `selects` 也是 `HashSet`，`System.out.println(set)` 打的是哈希桶顺序。
**想知道先后顺序得用 `List` 记。**（他自己这份数据上两种顺序刚好重合，所以从输出看不出来。）

## 四、为什么已选中的电台不会被重复选，以及那个 `else break`

外层是 `while (allAreas.size() != 0)`，如果一轮下来 `maxKey == null` 就 `break`。两个问题：

**（1）已入选的电台会不会再被选中？** 不会。它被选中时 `allAreas.removeAll(...)` 已经把它覆盖的地区全删了，
下一轮它的 `tempSet.retainAll(allAreas)` 交集必然是空，`tempSet.size() > 0` 挡住它。
实测 4 轮选出的 `order` 是 4 个不同的 key，没有重复。

**（2）那 `else break` 什么时候会触发？** 当**存在没有任何电台覆盖的地区**时。
手动往 `allAreas` 里塞一个没有电台覆盖的"武汉"，实测：

```
   traversal=[K3, K4, K5, K1, K2] -> rounds=5, order [K3, K2, K4, K5], leftover [武汉], selects=[K2, K3, K4, K5]
```

跑了 5 轮（第 5 轮全空 → `maxKey == null` → break），结果少了武汉，但**程序没有死循环**。
如果把那句 `else break` 删掉，这个输入就是无限循环 —— `allAreas` 永远不为空、永远选不出新电台。
**这个 `break` 是必须的，不是可选的保险。**

顺带：`allAreas` 本身是用 5 次 `addAll` 从各电台拼出来的，所以按构造不可能出现"没人覆盖的地区"。
也就是说这个 `break` 在他这份 `main` 里永远走不到 —— 只有把 `allAreas` 换成外部输入（或像上面那样手动加一个）才会触发。

## 五、贪心真的总是最优吗：实测 8.30% 的实例不是

在这份"电台选台"数据上贪心给了最优解（4 = 穷举最优）。但这是集合覆盖问题，贪心只是近似算法。
固定种子随机造 3,000 个实例（6..11 个地区、5..9 个电台，每个电台覆盖 1..⌊地区/2⌋ 个地区），
把贪心结果和穷举最优逐一比较：

```
贪心 = 最优      ：2,751 个实例（91.70%）
贪心 比最优多花钱：  249 个实例（ 8.30%）
最大差距          ：比最优多 2 个电台
```

所以"贪心 9 成时候够用、偶尔多花 1~2 个"是这类问题的常态。
**电台这份数据恰好落在 91.70% 那一侧**，跑它一个例子是看不出"贪心不保证最优"这件事的 ——
要体会就得随机造数据比对。

## 六、代价在哪：每一轮都把每个电台的地区整份搬一遍

内层循环体是

```java
tempSet.clear();
tempSet.addAll(broadcasts.get(key));   // 把电台的全部地区复制进 tempSet
tempSet.retainAll(allAreas);           // 再和未覆盖地区取交集
```

`retainAll` 是原地修改 `tempSet`，所以必须先 `addAll` 复制一份 —— 不能直接对电台的那个 `Set` 用 `retainAll`，
那样会把 `broadcasts` 里的数据本身改坏（这是个很容易犯的错）。

实测他这份数据：4 轮 × 5 个电台，总共搬运了 **52 个地区字符串**
（= 轮数 × 各电台地区数之和 = 4 × 13）。加上 `selects`/`removeAll`，量级是
`O(轮数 × Σ|电台地区| × 一次 HashSet 操作)`，而轮数最多就是电台数，所以是 `O(R × ΣS)`。

`HashSet.retainAll` 内部对每个元素做一次 `contains`（O(1) 平均），所以真正的开销在"复制"这一侧：
**每轮都无条件把每个电台的地区重抄一遍**，即使某个电台上一轮已经落选。
数据大了以后，这里是可以优化的点（缓存每个电台的剩余覆盖数，只在它的地区被别电台吃掉时才重算），
但那就不是"贪心"了，是带增量维护的贪心。

## 七、一句话记住

```
   每轮选"还能覆盖最多未覆盖地区"的电台，平局时用严格 < 保住了第一个 ——
   于是答案由 HashMap 的遍历顺序决定：同一份数据换一种构造方式，K1 会换成 K4（实测两种结果）；
   allAreas 一旦含有没人覆盖的地区，全靠那句 else break 才不死循环；
   这份数据上贪心=最优（4 个），但 3,000 组随机集合覆盖里有 8.30% 贪心比最优多花电台，最多差 2 个。
```
