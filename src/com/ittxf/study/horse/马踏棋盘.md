# 马踏棋盘（回溯 + 一步贪心排序：8 个数字的量级差）

> 对应程序：[HorseChessboard.java](./HorseChessboard.java)
> 骑士周游问题：马从某格出发，走满每一格且**每格只踩一次**。
> 这份实现是"递归回溯"外面套了一层 **Warnsdorff 启发式**：每次先把候选格按"它自己还能走几步"升序排一遍，
> 优先走最狭窄的那个（把宽裕的格子留到最后）。
> `main` 里 `X = Y = 8`、`row = col = 1`（传进去时 `-1`，所以实际是从 `(0,0)` 起）。

---

## 一、`main` 的输出

```
耗时: 80 ms
棋盘情况：
1	4	31	20	49	6	41	22
32	19	2	5	42	21	48	7
3	30	43	50	63	58	23	40
18	33	62	59	44	47	8	57
29	14	51	46	61	64	39	24
34	17	60	27	52	45	56	9
13	28	15	36	11	54	25	38
16	35	12	53	26	37	10	55
```

**棋盘是确定的（同一份代码每次跑出同一张），但那个"耗时"很飘**：反复跑同一份 `main`，实测落点在 36~107 ms
（同一批复刻实验里分别读到 78 / 79 / 80 / 81 / 36 / 44 / 107 ms），差异主要是 JIT 预热时机，
所以看这一列时只该看量级，别拿单次数字下结论 —— 下面第三节那张表用的是"递归调用次数"，那个才是确定的。

这张棋盘我逐项验过（复刻同一份逻辑跑完后校验）：

```
   耗时 79 ms，递归调用 47,156 次，回溯 47,092 次 -> 合法且覆盖全部 64 格
```

校验的两条硬规则：① 1..64 每个编号恰好出现一次；② 相邻两个编号所在的格子必须构成合法马步（行差 1 列差 2，或行差 2 列差 1）。
**全部通过** —— 这份程序在 8×8 上是真解出来了，不是靠回溯预算耗尽后剩下一张残局。

## 二、`next()` 的八条 `if` 就是马的八个方向

```java
if ((p1.x = curPoint.x - 2) >= 0 && (p1.y = curPoint.y - 1) >= 0) points.add(new Point(p1));
```

一个 `Point p1` 反复复用，靠**赋值表达式的返回值**同时完成"算坐标"和"判边界"。
这个写法读起来别扭但是对的：`(p1.x = ... ) >= 0` 先赋值再比较，两边都成立才 `add(new Point(p1))`（这里拷贝了一份，
所以下一次复用 `p1` 不会改掉已经存进 list 的那个点）。**最后这个 `new Point(p1)` 是必须的** ——
如果 `add(p1)` 直接加引用，八个候选会全部变成同一个点的最后一次状态。

## 三、那层排序值多少（实测）

把 `sortNext(ps)` 去掉，就是纯回溯穷举。同一个 8×8、同一起点：

| | 耗时 | 递归调用 | 结果 |
| --- | --- | --- | --- |
| 排序开 | 36 ms（第一次冷启动是 79 ms，见第一节；同一份代码重复跑在 36~107 ms 之间飘） | 47,156 | 走完 64/64 |
| 排序关 | **15,001 ms 超时中止** | **121,052,932** | 只填到 49/64 格，还没搜完 |

小一点的棋盘上差距更可读：

| 棋盘 | 排序开 | 排序关 |
| --- | --- | --- |
| 5×5 | 25 次调用（**一次都没回溯**） | 31,693 次调用，0 ms vs 9 ms |
| 6×6 | 1,523 次调用，5 ms | 1,219,046 次调用，358 ms |
| 8×8 | 47,156 次，36~80 ms | 15 秒没搜完 |

6×6 上排序把搜索量从 122 万砍到 1,523，**约 800 倍**；5×5 上直接砍成一条直线走到底（25 次调用 = 25 格，零回溯）。
这就是"往最窄的格子走"这条启发式的威力：**它把指数级的搜索树剪成了几乎一条链。**

代价也实测了 —— 排序本身要花钱：

```
   8x8 排序版：递归调用 47,156 次，next() 被调用 1,177,986 次（其中排序里的比较 565,415 次），耗时 81 ms
   平均每层递归要跑 next() 25.0 次
```

`compare` 里每次都现场调 `next(o1).size()` 和 `next(o2).size()`，而 `next()` 每调用一次就 `new ArrayList` 再 `add` 若干个 `Point`。
所以一层递归要生成 25 份候选列表 —— 想再快就把"候选数"缓存下来，别在比较器里重算。

## 四、起点挪一格，搜索量差 664 倍

8×8、排序开，只比起始格不同（实测）：

| 起点 | 递归调用 | 回溯 | 耗时 |
| --- | --- | --- | --- |
| (0,0) 角 | 47,156 | 47,092 | 36~107 ms |
| (0,1) | **71** | 7 | 0 ms |
| (1,1) | 81 | 17 | 1 ms |
| (0,2) | 771 | 707 | 3 ms |
| (2,3) | 168 | 104 | 0 ms |
| (3,3) 正中 | 441 | 377 | 1 ms |

**从角上出发比从旁边一格出发难 664 倍**，这跟直觉正好相反（角上不是最受限、按启发式应该最好走吗？）。
原因是启发式只在"当前候选之间"排序，它无法预知开局选错第一步以后要付多少回溯的账。
同一批起点把排序关掉：**6 个起点没有一个在 10 秒内搜完**（都是 3,100 万次调用以上、填到 44~52 格）。

## 五、`finished` 是 `static` 且从不复位 —— 第二次跑会打出假棋盘

```java
private static boolean finished;   // 只在类加载时是 false
...
if (step < X * Y && !finished) { chessboard[row][column] = 0; visited[row * X + column] = false; }
else finished = true;
```

`finished` 一旦被置为 true 就再也没人把它改回去。同一个 JVM 里跑第二次（实测）：

| | 耗时 | 递归调用 | 棋盘审计 |
| --- | --- | --- | --- |
| 第一次（干净） | 81 ms | 47,156 | 0 的格数 0，最大编号 64，64 个不同编号，无重复 ✓ |
| 第二次（`finished` 还是 true） | **0 ms** | **64** | 0 的格数 0，**最大编号 62，重复编号 2 个**（如 59 出现 2 次） |

机制：带着 `finished = true`，每次走到死路时那个 `if` 的条件 `!finished` 不成立，于是**既不擦格子、也不撤销 `visited`**
就直接返回，递归退化成"一条道走到黑"。第二次只调用 64 次、耗时 0 ms，看起来"秒出结果"，
实际打出来的棋盘上 59 和 62 各出现两次、根本没有 64 —— 一张非法棋盘。
（这份 `main` 只跑一次所以碰不到；把 `main` 改成跑两遍、或者把它当工具方法复用，立刻就能撞上。）
和 `GreedyAlgorithm` 那篇讲的 `HashSet` 顺序、`HuffmanCode` 那类 static 残留是同一类问题：**用 `static` 存搜索状态，就必须显式复位。**

## 六、它只能跑正方棋盘 —— 非正方直接越界崩

`next()` 里 `p1.x` 拿去和 `X` 比、`p1.y` 拿去和 `Y` 比，可传进来的 `Point` 是 `new Point(column, row)`，
也就是 **x 是列、y 是行**，而声明里 `X` 是行数、`Y` 是列数。两边正好用反了。实测：

```
   4x6（X=4 行, Y=6 列）：调用 7 次后 ArrayIndexOutOfBoundsException: Index 4 out of bounds for length 4
   6x4（X=6 行, Y=4 列）：Index 5 out of bounds for length 4
   2x8：Index 2 out of bounds for length 2
   3x4：Index 3 out of bounds for length 3
   4x5：Index 4 out of bounds for length 4
```

（`X×Y` 相等时两边判据重合，所以 8×8 一路正常，问题被完全掩盖。）
直接看 `next()` 的输出更清楚 —— 位置 `(列=3, 行=0)`：

```
   X=4 行 Y=6 列 时返回 (1,1) (2,2)                  ← 列 4、5 的合法格被 X 挡住了
   X=6 行 Y=4 列 时返回 (1,1) (2,2) (5,1) (4,2)      ← x=5 是"第 5 列"，可这张图只有 4 列，下一步就越界
```

正确写法是把判据改成 `x < Y`（列数）、`y < X`（行数）。

## 七、`visited[row * X + column]` 也是同一个行列混淆

一维 `visited` 要按"每行有 `Y` 个格子"来算偏移，应该是 `row * Y + column`。写成 `row * X` 之后，
X=4 行 Y=6 列的 24 个格子只映射到 **18 个下标**，实测有 6 个下标被两格共用：

```
   下标 4 被 [(0,4), (1,0)] 共用
   下标 5 被 [(0,5), (1,1)] 共用
   下标 8 被 [(1,4), (2,0)] 共用   …
```

也就是说 **(0,4) 和 (1,0) 是同一个"已访问"标记** —— 踩了其中一个，另一个会被误认为已经走过。
正方棋盘上 `X == Y`，两个公式重合，所以同样被掩盖。

（注意别搞混：这两处的根因都是"行数列数用反"，但表现不同 —— 第六节是数组越界崩溃，第七节是标记串味。
真跑非正方时先在第六节就崩了，所以第七节这个坑平时看不见。）

## 八、无解的棋盘：它会把空间穷举完然后留一张全 0

| 棋盘 | 递归调用 | 回溯 | 最终 |
| --- | --- | --- | --- |
| 3×3 | 15 | 15 | 填了 0/9 格 |
| 4×4 | 2,223 | 2,223 | 填了 0/16 格 |

这两张棋盘确实不存在骑士周游，程序把所有分支试完后**逐层把格子擦回 0**，打印出一张空棋盘 —— 行为是对的。
但要注意它**不打印任何"无解"提示**（`main` 只有耗时和棋盘），所以看到一张全 0 棋盘得自己判断这是"无解"而不是"跑挂了"。
回溯次数和调用次数相等（15/15、2223/2223）正好说明：**每一层都被撤销过，没有一层留下来。**

## 九、启发式不是万能：12×12 就搜不动了

排序开、从 (0,0) 起，20 秒预算（实测）：

| 棋盘 | 结果 | 递归调用 | 填了多少格 |
| --- | --- | --- | --- |
| 8×8 | 完成 | 47,156 | 64/64 |
| 10×10 | 完成（51 ms） | 50,444 | 100/100 |
| 12×12 | **超时中止** | 21,731,151 | 131/144 |
| 14×14 | **超时中止** | 20,353,262 | 182/196 |
| 16×16 | **超时中止** | 22,442,271 | 238/256 |

有意思的是三张超时图的中止状态都停在"填了 131 / 182 / 238 格"这个量级 ——
说明它**一路顺到很后面才卡住**，Warnsdorff 在大棋盘上依然有效，只是最后总有一段把搜索掀翻，
而这份实现没有任何补救手段（标准做法是并列候选时随机挑一个、或者失败后从头重启若干次）。
顺带确认一下栈：递归深度最多就是格子数（8×8 是 64 层），
和汉诺塔笔记里实测的"默认栈能撑约 2 万层"相比完全不是问题 —— 这里的瓶颈从来是搜索量，不是栈深。

## 十、一句话记住

```
   回溯 + Warnsdorff：8x8 上实测把 1.2 亿次调用压到 4.7 万次（6x6 是 800 倍），代价是每层要跑 25 次 next()；
   从 (0,0) 出发比从 (0,1) 难 664 倍，开局那一步的选择比启发式本身还关键；
   finished 是 static 且不复位，第二次跑只调用 64 次就打出一张"59 出现两次"的假棋盘；
   next() 用列去比 X、用行去比 Y，visited 用 row * X —— 只有正方棋盘能掩盖这个行列互换，
   实测任何 X≠Y 的配置都会在几步之内 ArrayIndexOutOfBoundsException；
   无解时会留下一张全 0 棋盘且不提示，12×12 以上贪心排序不够用、需要随机重启。
```
