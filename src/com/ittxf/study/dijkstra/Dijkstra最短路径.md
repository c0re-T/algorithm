# Dijkstra 最短路径（三个数组来回改，`65535` 既是无穷大也是天花板）

> 对应程序：[DijkstraAlgorithm.java](./DijkstraAlgorithm.java)（同文件里还有 `Graph` 和 `VisitedVertex`）
> 7 个顶点 A..G、10 条边的**对称**邻接矩阵，`N = 65535` 表示"无边"。`main` 里 `dijkstra(6)` 是从 **G** 出发。
> 三个数组：`alreadyArr`（谁已经定稿）、`distance`（起点到各点目前最短）、`pre`（每个点的前驱）。

---

## 一、`main` 的输出

```
alreadyArr = [1, 1, 1, 1, 1, 1, 1]
distance = [2, 3, 9, 10, 4, 6, 0]
pre = [6, 6, 0, 5, 6, 6, 0]
A (2)
B (3)
C (9)
D (10)
E (4)
F (6)
G (0)
```

和一份独立实现（同样把 65535 当无边，但每步都显式判断"还有没有可达的候选"）**逐个起点对照，7 个起点全部一致**：

| 起点 | 他算出的 distance | 参考 | |
| --- | --- | --- | --- |
| A | 0 5 7 12 6 8 2 | 相同 | 一致 |
| B | 5 0 12 9 7 9 3 | 相同 | 一致 |
| C | 7 12 0 17 8 13 9 | 相同 | 一致 |
| D | 12 9 17 0 9 4 10 | 相同 | 一致 |
| E | 6 7 8 9 0 5 4 | 相同 | 一致 |
| F | 8 9 13 4 5 0 6 | 相同 | 一致 |
| G | 2 3 9 10 4 6 0 | 相同 | 一致 |

## 二、七轮下来 `distance` 是怎么变的

`dijkstra(6)` 从 G 出发，实测逐轮（`update(index)` 就是拿 `index` 那一行去松弛）：

| 轮 | 选定 | 依据 | 之后 `distance`（— 表示还是 65535） |
| --- | --- | --- | --- |
| 0 | G（起点直接定稿） | `update(G)` | A=2 B=3 E=4 F=6 — — 0 |
| 1 | A（2 最小） | A-B 5 → 7 > 3 不动；A-C 7 → **C=9** | 2 3 9 — 4 6 0 |
| 2 | B（3） | B-D 9 → **D=12** | 2 3 9 12 4 6 0 |
| 3 | E（4） | E-C 8 → 12 > 9 不动；E-F 5 → 9 > 6 不动 | 2 3 9 12 4 6 0 |
| 4 | F（6） | F-D 4 → 6+4=**10 < 12**，D 改前驱为 F | 2 3 9 10 4 6 0 |
| 5 | C（9） | 邻居 A、E 都已定稿，什么都没改 | 2 3 9 10 4 6 0 |

数一下总账（实测）：**49 次 `len` 计算**（7 轮 × 每轮扫 7 列），其中**只有 7 次真的写进 `distance`**。
最后 `pre = [6, 6, 0, 5, 6, 6, 0]` 翻成人话：A←G、B←G、C←A、D←F、E←G、F←G、G←(0)。

第 4 轮那次"12 变 10"是 Dijkstra 的关键动作：**已经定稿过的 D 还没被选走之前，还能被后来的点改短**。
一旦某个点被 `updateArr()` 选中定稿，`!visitedVertex.in(j)` 就再也拒绝任何更新 —— 这也是它对负权边失效的原因（第四节）。

## 三、`65535` 同时当"无穷大"和"上限"，路径一长就把可达算成不可达

`update` 里那句

```java
len = visitedVertex.getDis(index) + matrix[index][j];
if (len < visitedVertex.getDis(j) && !visitedVertex.in(j)) { ... }
```

`distance[j]` 的初值是 65535，任何 `len ≥ 65535` 都进不来。构造一条两段的路径：

```
A-B = 40000, B-C = 40000      （A 到 C 真实是 80000）
他的 distance = [0, 40000, 65535]      ← C 还是初值，show() 会打成 "N"
参考          = [0, 40000, 80000]

换成 A-B = B-C = 30000（合计 60000 < 65535）
他的 = [0, 30000, 60000]，参考 = [0, 30000, 60000]   ← 这时才对
```

**阈值就是 65535 这一格**：不是负边、不是溢出（`65535 + 65535 = 131070` 在 `int` 里稳得很），
而是"用来表示无穷大的那个数，同时也就是允许的最大路径长度"。
`show()` 里 `if (i != 65535) 打印数字 else 打印 "N"` 把这个语义钉得更死 —— 超过 65535 的点会伪装成"不连通"。
想撑开这个上限，就把 `N` 换成 `Integer.MAX_VALUE / 2`（除 2 是为了让 `dis + weight` 不溢出）。

## 四、有负权边时它给的是错答案，而且错得很安静

给他那张图加一条**有向**负边 `E→A = -10`（刻意不成环，这样最短路径是良定义的），从 G 出发实测：

```
他的 Dijkstra ：A=2   B=3  C=9  D=10  E=4  F=6  G=0
朴素参考实现  ：A=2   B=3  C=9  D=10  E=4  F=6  G=0      ← 同样的贪心，同样错
Bellman-Ford  ：A=-14 B=-5 C=-3 D=2   E=-4 F=-2 G=-8     ← 正确答案
```

机制就在第二节末尾那句：A 在第 1 轮以 2 定稿，之后 E 变成 4、`E→A=-10` 本可以把 A 拉到 -6，
但 `!visitedVertex.in(j)` 拒绝再碰 A。**贪心选最小这一步的正确性依赖"边权非负"**，
所以两个"看起来不一样"的实现给出同一个错答案，这不能互相验证 —— 得换算法。

## 五、图不连通时 `updateArr()` 返回的是上一轮的顶点

```java
public int updateArr() {
    int min = 65535, index = 0;                    // index 没有每轮复位
    for (int i = 0; i < alreadyArr.length; i++)
        if (alreadyArr[i] == 0 && distance[i] < min) { min = distance[i]; index = i; }
    alreadyArr[index] = 1;
    return index;
}
```

把 C 的所有边删掉，从 G 出发实测：

```
他的   distance ：A=2 B=3 C=不可达 D=10 E=4 F=6 G=0
参考   distance ：A=2 B=3 C=不可达 D=10 E=4 F=6 G=0     ← 数字是对的
他的 alreadyArr ：[1, 1, 0, 1, 1, 1, 1]                ← C 从来没被标成已访问
```

为什么数字没错？因为剩余轮次里 `index` 退回到 0（也就是 A），而 `update(A)` 只会拿 A 那一行去松弛，
`!in(j)` 又挡住了所有已定稿的点，于是这几轮是**纯粹的重复劳动**，不改任何值。
`alreadyArr` 里 C 那个 0 也是同理：它被跳过，但 `distance[C]` 保持 65535，`show()` 打出来还是 "N"。

**这和 Prim 那份的"忘了复位"后果不一样**：Prim 的 `h1/h2` 不复位会**当场打印一条不存在的边**并给总权值加上 10000，
而这里复用的是起点、又不产生新增长度，所以数字侥幸保住。
换句话说：不复位这件事本身是错的，只是这一份程序错得不明显 —— 把它当"安全"来记就记错了。

## 六、`VisitedVertex.show()` 里私藏了一份顶点表

```java
char[] vertex = {'A', 'B', 'C', 'D', 'E', 'F', 'G'};   // 写死在 show() 里
int count = 0;
for (int i : distance) { ... System.out.println(vertex[count] + " (" + i + ")"); count++; }
```

`VisitedVertex` 根本不知道图的顶点叫什么，它自己抄了一份 7 个名字的表。实测换一张 8 个顶点的图：

```
   distance 算得对（[0, 1, 2, 3, 4, 5, 6, 7]），
   但 show() 的循环到第 8 个名字时 ArrayIndexOutOfBoundsException: Index 7 out of bounds for length 7
```

计算是对的、**打印才崩** —— 这种"算法正确、展示层写死了输入规模"的组合最容易被忽略，
因为换数据测试时常常只看算得的数组，不看打印。改法：把 `vertex` 传给 `VisitedVertex`，或者让 `show()` 打下标。

顺带 `pre` 的两个显示陷阱：起点的 `pre` 是默认值 0（`pre[6] = 0`，看起来像"前驱是 A"，其实它没有前驱）；
没连通的点 `pre` 也是 0。`show()` 没打 `pre`，所以这两处不会被看见，但拿 `pre` 还原路径时得自己挡掉。

## 七、代价：`V²` 扫表，没有堆

`update` 每轮扫一整行（V 格），`updateArr` 每轮扫整个 `alreadyArr`（V 格），一共 V 轮 → `O(V²)`。
实测（连通随机图，每张都拿参考实现核对过）：

| V | 单次 `dijkstra` | 备注 |
| --- | --- | --- |
| 200 | 1 ms | |
| 400 | 1 ms | |
| 600 | 3 ms | |
| 800 | 0~1 ms | 另跑 800 次（每点做一次单源）合计 413 ms |

这个量级说明一件事：**朴素数组版 Dijkstra 在稠密矩阵上并不慢**，因为它的瓶颈是"扫矩阵"，
而矩阵本来就必须存在。真正划算与否看的是要单源还是全源（Floyd 笔记第六节有同一批图上的对照：
V=800 时 800 次 Dijkstra 要 413 ms，一次 Floyd 只要 146 ms）。
堆版 `O(E log V)` 的优势要等到图很稀疏、或者只要单源且 E << V² 时才显现。

## 八、和 Prim / Floyd 放一起看

| | 顶点集划分 | 每轮的动作 | `N` 的写法 | 复位漏了的后果 |
| --- | --- | --- | --- | --- |
| Prim | 已进树 / 未进树 | 找**跨堆最小边**，累加权值 | `10000` | 复述上一条边 + 总权值凭空 +10000 |
| Dijkstra | 已定稿 / 未定稿 | 找**未定稿里 distance 最小**，再松弛它那一行 | `65535` | 退回起点重复松弛，数字侥幸没错 |
| Floyd | 没有"已选"概念 | 三重循环枚举中继点 | `65535`，但**对角线必须填 0** | 见 Floyd 笔记 |

三个都是"矩阵 + 一轮一个点"的形状，最容易串味的地方恰恰是那个无穷大常量：
Prim 用 10000、这两份用 65535、Kruskal 用 `Integer.MAX_VALUE`，三份混着看代码时得先确认是哪一份。

顺手核了一件好事：**Prim 那份矩阵和这份 Dijkstra 的矩阵是同一张图** ——
逐条边上三角比对，两边都是 10 条边、权值完全一致（`A-B 5、A-C 7、A-G 2、B-D 9、B-G 3、C-E 8、D-F 4、E-F 5、E-G 4、F-G 6`），
只是一个把无边写成 10000、另一个写成 65535。
所以 Prim 笔记里那条总权 25 的生成树，正好可以拿来和这份的 `distance` 对照看一件事：**生成树不保最短路径**。
Prim 选出来的六条边是 `A-G(2) G-B(3) G-E(4) E-F(5) F-D(4) A-C(7)`，在这棵树里 A 到 D 只能沿 `A→G→E→F→D` 走，花 2+4+5+4 = **15**；
而图上真正的 A→D 最短路是 **12**（`A→G→F→D` = 2+6+4，用的 `G-F(6)` 这条边根本没进生成树）。
最小生成树保证的是"所有边加起来最省"，不是"任意两点之间最快" —— 这两个目标在这张图上就差了 3。
只有 Kruskal 那份是另一张 12 条边的图（见它那篇笔记第一节末尾的说明）。

## 九、一句话记住

```
   7 轮 49 次松弛计算里只有 7 次真的改到 distance，"定稿后不再更新"是它的全部纪律，也是它怕负边的原因；
   和参考实现逐起点对过，7 个起点全一致；矩阵是完全对称的 10 条边，可以放心和 Floyd 交叉验证；
   65535 既是无穷大也是天花板，实测 40000+40000 的路径会被判成"不可达"；
   updateArr 的 index 和 show() 的顶点表都有隐患：前者在不连通时退回到起点（数字侥幸不错，白跑几轮），
   后者写死 7 个名字，8 个顶点的图会算对了却打印崩。
```
