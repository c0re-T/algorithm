# 和为正的最长子数组（前缀和 + 哈希表，但每步扫全表 → O(n × 不同前缀和个数)）

> 对应程序：[LongestSubarraySumPositive.java](./LongestSubarraySumPositive.java)
> `main` 用 `{-1,-1,-1,1,1}`，实测：
>
> ```
> 3
> ```
>
> 最长的一段是 `{-1,1,1}`（和为 1），从下标 2 到 4。

---

## 一、把"和为正"翻译成前缀和比大小

子数组 `(j, i]` 的和 = `preSum[i] - preSum[j]`。要它为正，就是要 `preSum[i] > preSum[j]`；要它最长，就是要**满足这个不等式的最小的 j**。

```java
hashMap.put(0, 0);                  // 空前缀：前缀和 0 出现在下标 0
int preSum = 0, maxLen = 0;
for (int i = 1; i <= nums.length; i++) {
    preSum += nums[i - 1];
    for (Map.Entry<Integer, Integer> entry : hashMap.entrySet()) {
        if (preSum > entry.getKey()) {          // 严格大于
            maxLen = Math.max(maxLen, i - entry.getValue());
        }
    }
    if (!hashMap.containsKey(preSum)) {         // 只记第一次出现的下标
        hashMap.put(preSum, i);
    }
}
```

注意下标口径：`i` 从 1 到 n，`preSum` 是"前 i 个元素的和"，所以 `put(0, 0)` 表示"前 0 个元素的和是 0"。长度算出来是 `i - entry.getValue()`，正好是元素个数，不需要 ±1。这和 `p560`/`p437` 的口径一致。

## 二、两个"只"字各自值多少

**① `preSum > key` 不能写成 `>=`。** 和为 0 不算"为正"。实测 20,000 组随机数组（长度 0..29、值 −3..3）：

```
改成 >= ：差异 = 5,823（29.1%）
最小反例：{0}，真值 0，改成 >= 给 1
```

**② 同一个前缀和只记第一次出现的下标。** 后来的下标更大，`i - value` 只会更短，记了也没用；但覆盖掉第一次的就会丢答案：

```
改成每次覆盖：差异 = 10,262（51.3%）
反例：{1,-1,1}，真值 3，覆盖版给 1
```

`{1,-1,1}` 的前缀和序列是 `0,1,0,1`。前缀和 0 第一次在下标 0、第二次在下标 2；覆盖之后表里只剩 `(0→2)`，于是 i=3 时只能算出长度 1，而正确答案是从下标 0 到 3 的整段（和为 1）。

**③ `put` 不能挪进 entrySet 循环里。** 实测直接 `ConcurrentModificationException` —— 遍历 HashMap 的同时改它的结构，fail-fast 迭代器立刻抛。当前写法把 `put` 放在循环之后，是安全的。

## 三、随机对拍与边界

20,000 组随机数组，与两种独立参考对比：

```
vs 枚举所有子数组（O(n²)）        差异 = 0
vs 前缀和排序参考（O(n log n)）   差异 = 0
```

| 输入 | 输出 |
| --- | --- |
| 空数组 | 0 |
| 全负 `{-2,-3}` | 0 |
| 全 0 | 0 |
| 全正 `{1,2,3}` | 3 |
| `{0,1}` | 2 |
| `null` | `NullPointerException` |

`{0,1}` 给 2 值得留意：整段和为 1 > 0，所以 0 虽然不贡献正值，但它可以被包含在答案里。判据是**整段的和**，不是"每个元素都为正"。

**int 溢出**：`{1000000000, 1000000000, 1000000000}` 实测给 2，真值 3。三个 1e9 相加是 3e9，越过 `Integer.MAX_VALUE` 变成负数，前缀和之间的大小关系就乱了。这份实现虽然只"比大小"不"求区间和"，但前缀和本身仍然是累加出来的，照样溢出。题面若允许 1e9 量级的值，`preSum` 和 map 的 key 都得换 long（`p437` 就是这么做的）。

## 四、复杂度：这份不是 O(n)

每走一步都要遍历整张哈希表，所以总时间是 `O(n × 表里不同前缀和的个数)`。表里有多少个 key，完全由数据决定：

| 数据 | n | 表里 key 数 | 他的版本 | 前缀和排序版 | 逐起点暴力 |
| --- | --- | --- | --- | --- | --- |
| 随机 ±3 | 2,000 | — | 0 ms | 1 ms | 1 ms |
| 随机 ±3 | 8,000 | — | 2 ms | 2 ms | 15 ms |
| **全 1** | 2,000 | 2,000 | 3 ms | 0 ms | 0 ms |
| 全 1 | 4,000 | 4,000 | 15 ms | 0 ms | 3 ms |
| 全 1 | 8,000 | 8,000 | 57 ms | 0 ms | 15 ms |
| 全 1 | 16,000 | 16,000 | **227 ms** | **0 ms** | 62 ms |

随机 ±3 的数组前缀和来回摆动，n=5,000 时表里只有 **180 个**不同前缀和，所以扫表很便宜，看起来像 O(n)。全 1 数组的前缀和严格递增，n 个元素就有 n 个 key，扫表总量变成 `n²/2`：规模翻一倍耗时翻四倍（3→15→57→227），**实测就是二次的**。

n=16,000 时它比 `O(n²)` 的逐起点暴力还慢 3.7 倍（227 ms vs 62 ms）—— 因为暴力的内层循环是纯数组访问，而这份每步都在遍历 HashMap 的 Entry 对象。而 `O(n log n)` 的前缀和排序版全程 0 ms。

正确的线性做法是维护"前缀和的单调递减栈"：只有比栈顶更小的前缀和才值得入栈（更大的既晚出现又更大，永远不可能给出更长的答案），然后对每个 i 在栈上二分找第一个小于 `preSum[i]` 的位置。那是 `O(n log n)`；要做到严格 `O(n)` 需要更细的单调结构。**这份实现的"哈希表"给人一种 O(n) 的错觉，实际不是。**

## 五、一句话记住

```
   preSum[i] > preSum[j] 且 j 尽量小；put(0,0) 是空前缀，长度 = i - value；
   > 改成 >= 错 5,823/20,000（{0} → 1）；覆盖第一次下标错 10,262/20,000（{1,-1,1} → 1）；
   put 挪进 entrySet 循环 → ConcurrentModificationException；
   20,000 组与暴力和 O(n log n) 参考都 0 差异；空/全负/全 0 给 0，null NPE；
   preSum 是 int：三个 1e9 给 2（真值 3）；
   每步扫全表 → O(n × key 数)：随机 ±3 只有 180 个 key 像线性，
   全 1 数组 n=16,000 有 16,000 个 key → 227 ms，比暴力 62 ms 还慢，排序版 0 ms。
```
