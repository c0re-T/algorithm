# LeetCode 415 字符串相加（把小学竖式写成代码）

> 对应程序：[LeetCode415_AddStrings.java](./LeetCode415_AddStrings.java)
> 题目：给两个用字符串表示的非负整数 `num1`、`num2`，返回它们相加后的字符串。
> 约定**不能**把字符串直接转成整数（也就是不许 `parseInt` 作弊）。
> 题面约束是"两个串都只含数字、没有前导零、长度 1..100"，这份实现满足该约定；
> 下面有几节专门把输入伸出约定之外，看它会变成什么。

---

## 一、`main` 里那一次：`"456" + "77"`

实测输出 `533`。逐位推演（`i`/`j` 是两个串**从个位往前**的下标）：

| 轮 | i | j | x | y | forward(进位前) | sum | 新 forward | append |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 2 | 1 | 6 | 7 | 0 | 13 | 1 | `3` |
| 2 | 1 | 0 | 5 | 7 | 1 | 13 | 1 | `3` |
| 3 | 0 | -1 | 4 | 0 | 1 | 5 | 0 | `5` |
| 4 | -1 | -1 | — | — | 0 | 循环条件全不成立，退出 | | |

`StringBuilder` 里攒下的是 `"335"`，最后一句 `.reverse().toString()` 变成 `"533"`。

**为什么要反：加法只能从低位算，但字符串是从高位存的。** 下标从尾往头走，
得到的数字自然也是"个位在前"，所以要倒过来才是答案。这个 reverse 不是可选装饰 ——
第五节实测不写它会得到什么。

---

## 二、循环条件那三个 `||`，缺一个都会错

```java
while (i >= 0 || j >= 0 || forward != 0)
```

三个条件各自挡一种情况：

| 条件 | 挡的是 |
| --- | --- |
| `i >= 0` | num1 还没加完 |
| `j >= 0` | num2 还没加完 |
| `forward != 0` | **两边都加完了，但顶上还挂着最后那个进位** |

把第三个条件删掉（`while (i >= 0 || j >= 0)`），实测：

| num1 | num2 | 原实现 | 删掉第三个条件 | 正确答案 |
| --- | --- | --- | --- | --- |
| `"456"` | `"77"` | `"533"` | `"533"` | 533 |
| `"12"` | `"87"` | `"99"` | `"99"` | 99 |
| `"99"` | `"1"` | `"100"` | **`"00"`** | 100 |
| `"5"` | `"5"` | `"10"` | **`"0"`** | 10 |
| `"999"` | `"1"` | `"1000"` | **`"000"`** | 1000 |

前两组恰好不进位，所以看不出差别 —— **这就是那种"跑了两组测试就以为对了"的 bug**。
一旦最高位产生进位，答案直接少一位，而且因为丢的是最高位，剩下的 `"00"` 看起来像个合法数字，
连长度异常都不明显（`"100"` → `"00"` 才是正确的长度信号）。

`forward != 0` 让循环多走一轮，那一轮里 `x = y = 0`，`sum = 0 + 0 + 1 = 1`，正好把最高位补上。

## 三、`charAt(i--) - '0'`：一行里塞了三件事

```java
int x = i >= 0 ? num1.charAt(i--) - '0' : 0;
```

拆开看是：

1. `i >= 0 ?` —— 这个串已经加完了就**补 0**，于是两个不等长的串不需要先对齐补零；
2. `num1.charAt(i)` —— 取当前位的字符；
3. `- '0'` —— 字符减去 `'0'`（ASCII 48）得到它的数字值。`'7' - '0' = 55 - 48 = 7`。
   Java 里 `char` 参与算术会自动提升成 `int`，所以这个写法是合法的，也是题目禁止 `parseInt` 时
   唯一的取数方式。

`i--` 写在括号里，只有**真的取了字符**才自减。`i < 0` 时走的是 `: 0` 分支，`i` 保持 -1 不动，
所以 `i >= 0` 这个判断在后续每一轮都稳定为 false —— 不会出现"减过头又变正"的问题。

相邻字符的值实测：

```
'0' - '0' = 0      '9' - '0' = 9
'/' - '0' = -1     ':' - '0' = 10      ← 数字区间外面一格就是这个值
```

`'/'` 和 `':'` 是 `'0'` 和 `'9'` 的邻居，值分别是 -1 和 10。这解释了第八节里
"非法字符不会报错，只会变成一个不像它的数"。

## 四、进位只可能是 0 或 1

代码里 `forward = sum / 10`。穷举所有可能的 `x, y ∈ 0..9`、`forward ∈ 0..1`：

```
最大 sum = 19（9 + 9 + 1）      最大 sum / 10 = 1
```

所以 `forward` 永远是 0 或 1，`sum % 10` 永远落在 0..9 —— 每轮 `append` 的都是**一个**数字字符。
这是整套"逐位加"能成立的前提：一旦进位能到 2，`append(sum % 10)` 就会写错值。

（作为对照：如果允许 `forward` 取到 9，`sum` 最大 27、进位最大 2，逻辑就崩了。
它取不到 9 是因为上面那行 —— 这是一个自洽的归纳，不是巧合。）

## 五、`.reverse()` 不能省

去掉最后那句 `stringBuilder.reverse()`，实测：

| num1 | num2 | 正确 | 不 reverse |
| --- | --- | --- | --- |
| `"456"` | `"77"` | 533 | **`"335"`** |
| `"120"` | `"30"` | 150 | **`"051"`** |

`"335"` 正好是 `"533"` 的倒影，因为它就是"个位在前"的中间结果。
值得注意的是 `"051"`：真实答案 150，倒过来写成 051，**长度没错、每一位数字也没错，只是顺序反了**，
所以拿 `result.length()` 或"数字集合"去断言都发现不了，只能逐字符比。

## 六、为什么要用字符串：`long` 在 19 位就死

```
Long.MAX_VALUE = 9,223,372,036,854,775,807      （19 位）
Long.parseLong("30 个 9")  -> NumberFormatException: For input string: "999999999999999999999999999999"
本方法 addStrings("30 个 9", "1") -> 1000000000000000000000000000000   （1 后面 30 个 0，正常）
```

题目禁止转换是有道理的：`"456"+"77"` 用 `Integer.parseInt` 一行就能写完，
但 100 位的数字串（题面允许的最大长度）早就超出任何基本类型，只能逐位加。

**和 `BigInteger` 比一次（超出题面 100 位的限制，纯看算法代价）：**
20 万位的数相加（200,000 位 + 199,999 位），结果与 `BigInteger` 完全一致：

```
本方法：6 ms
BigInteger：981 ms
```

差 163 倍不是加法慢，是 `BigInteger` 要把字符串先解析成内部的大整数值、按 32 位 limb 逐位加、
最后还要格式化回十进制字符串。这份实现全程只碰 `char` 和 `int`，除 `StringBuilder` 自己之外
没有任何额外分配。**换句话说：这道题的"字符串"不是限制，是它比通用大整数库快的原因。**

## 七、循环次数：最多 `max(m, n) + 1`

| num1 | num2 | 长度 | 循环轮数 |
| --- | --- | --- | --- |
| `"456"` | `"77"` | 3 / 2 | 3 |
| `"999"` | `"9"` | 3 / 1 | 4 |
| `"1"` | `"99999"` | 1 / 5 | 6 |

规律是：不进位时 `max(m, n)` 轮，最后一轮还进位就多一轮。
所以时间是 `O(max(m, n))`，空间是结果字符串本身 `O(max(m, n) + 1)`。

## 八、不校验输入：非法字符会"变成"另一个数字

方法对入参一个字都没检查。实测（右边同时列出 `BigInteger` 的态度）：

| num1 | num2 | 本方法 | BigInteger |
| --- | --- | --- | --- |
| `"12a"` | `"3"` | **`"172"`** | 抛 `NumberFormatException` |
| `"1 2"` | `"3"` | **`"06-5"`** | 抛 `NumberFormatException` |
| `"99"` | `"x"` | **`"171"`** | 抛 `NumberFormatException` |

`"12a" + "3"` 为什么会得出 `"172"`？因为 `'a' - '0' = 49`，而 49 在这一套逻辑里
就等价于"这一位是 9，进位 4"：

```
第 1 轮：x = 49('a'), y = 3('3')  -> sum = 52  -> append 2, forward = 5
第 2 轮：x = 2 ('2'), y = 0        -> sum = 7   -> append 7, forward = 0
第 3 轮：x = 1 ('1'), y = 0        -> sum = 1   -> append 1
结果 "271" 反转 -> "172"
```

**整个过程一声不响，输出还是个"像模像样"的数字串。** 这是所有底层字符运算的通病：
`- '0'` 是纯算术，它不知道什么是数字。

`"1 2" + "3"` 更离谱，输出里出现了 `-`：空格 `- '0' = -16`，
`sum = -16` 时 `forward = -16 / 10 = -1`（Java 整数除法向零截断），
`sum % 10 = -6`（Java 的 `%` 符号跟被除数），而 `append(int)` 会把 `-6` 当成**两个字符** `"-6"` 写进去，
于是答案里混进了负号。

按题面约束（只含数字）这些都不会发生，所以不算 bug；但**如果这个方法被拿去处理外部输入，
它不会拒绝，只会安静地给出一个错答案** —— 校验得由调用方做。

## 九、前导零和空串：与 BigInteger 的三处分歧

题面排除了前导零和空串，但代码本身会照原样算（实测，右边是 `BigInteger` 的规范化结果）：

| num1 | num2 | 本方法 | BigInteger | 一致？ |
| --- | --- | --- | --- | --- |
| `"456"` | `"77"` | `"533"` | `"533"` | 是 |
| `"0"` | `"0"` | `"0"` | `"0"` | 是 |
| `"1"` | `"9"` | `"10"` | `"10"` | 是 |
| `"99"` | `"1"` | `"100"` | `"100"` | 是 |
| `"999"` | `"999"` | `"1998"` | `"1998"` | 是 |
| `"1"` | `"1000000"` | `"1000001"` | `"1000001"` | 是 |
| `""` | `"123"` | `"123"` | `"123"` | 是 |
| `"007"` | `"1"` | **`"008"`** | `"8"` | 否 |
| `"000"` | `"000"` | **`"000"`** | `"0"` | 否 |
| `""` | `""` | **`""`**（空串） | `"0"` | 否 |

两个值得记住的性质：

- **不进位的前导零会被原样保留**（`"007"+"1" = "008"`），因为这个方法压根不理解"零值"，
  它只是逐位搬数字。
- **两个空串相加返回空串**，不是 `"0"`。因为三个循环条件全为 false，一次都不进入，
  `reverse()` 作用在空的 builder 上还是空。LeetCode 的约束（长度 ≥ 1）挡住了这种输入，
  但作为通用工具方法这就是个坑 —— 拿它当竖式加法器要自己挡空串。

## 十、一句话记住

```
   从个位往左加、低位先写、最后 reverse —— 这是"字符串存高位、加法从低位"这对矛盾的解法；
   三个循环条件里的 forward != 0 专门负责最高位那个进位，删掉后 "99"+"1" 会变成 "00"；
   -'0' 是纯算术，非法字符不会报错只会变成别的数字（'a' 当作 9 并进 4）；
   题面禁止 parseInt 是因为 long 只能到 19 位，而这套写法 20 万位只要 6ms。
```
