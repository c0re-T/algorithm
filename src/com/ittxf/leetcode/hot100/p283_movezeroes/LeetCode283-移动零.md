# LeetCode 283 移动零（两段式覆盖，和"额外数组"那份的唯一区别就是省一份内存）

> 对应程序：[LeetCode283_MoveZeroes.java](./LeetCode283_MoveZeroes.java)
> `main` 用 `[0,1,0,3,12]`，实测打印 `[1, 3, 12, 0, 0]`。原地修改，不返回值的 `void` 方法。

---

## 一、两段式在干什么

```java
int index = 0;
for (int i = 0; i < nums.length; i++) if (nums[i] != 0) { nums[index] = nums[i]; index++; }   // ①非零前移
for (int i = index; i < nums.length; i++) nums[i] = 0;                                        // ②后面补零
```

`index` 是"下一个非零元素该放的位置"。第一趟把整个数组压成"非零的紧密前缀"，第二趟把尾巴抹平。
这就是**稳定划分**（stable partition）：非零元素之间的相对顺序保持不变，只是零被赶到后面。

## 二、和"额外数组"那份参考实现对拍

固定种子 20,000 组随机数组（长度 2..15，约 1/4 是 0，其余 1..9），与"另开一个数组按顺序抄非零、剩下填 0"的参考实现比：

```
   结果不同 —— 0 次
```

也就是**顺序覆盖没有破坏任何东西**。原因在于 `index <= i` 恒成立：写目标永远在读目标的同一格或左边，
所以"已经读过的值"不可能被"还没读到的值"覆盖掉。这一条值得单拎出来，因为它是这类原地压缩能成立的唯一理由
（反过来，把非零元素往尾部堆、从右往左扫的同时从左往右写，就会互相踩）。

## 三、"自己写自己"发生了多少次

`nums[index] = nums[i]` 在 `index == i` 时是一次无意义的自赋值。实测：

| 输入 | 自写次数 | 说明 |
| --- | --- | --- |
| `[0,1,0,3,12]` | 0 | 第一个非零在 `i=1`，此时 `index` 已是 0，之后一直错开 |
| `[1,2,3,4]` | 4 | 全程没有零 → `index` 始终等于 `i`，整趟都在原地自写 |
| `[0,0,0]` | 0 | 一次都没进 `if`，第二趟把 0..2 全写 0（值其实没变） |

**结论：没有零的数组会把每一格都"原地重写一遍"**。要省掉它就得改成"只在 `index != i` 时赋值"，
或者用交换写法 —— 但这两种都是可读性换一点点无谓写入，实测这份方法本身在毫秒以下，不值得为此加判断。
（这里给的是"这个自写存在"的事实，不是"它有害"的结论。）

## 四、注释里那份"额外数组"版本

```java
int[] copy = new int[nums.length];
Arrays.fill(copy, 0);
... 把非零抄进 copy ...
for (int i = 0; i < nums.length; i++) nums[i] = copy[i];
```

行为与主方法完全等价（第二节对拍用的就是它的同构版），差别只在**多要一份 `O(n)` 内存**、
而且要走三趟（`fill` + 抄 + 回写）。题面明确要求"必须原地操作，不能创建新数组"，所以那份不符合要求 ——
它的价值是把"稳定划分"这个语义写得很直白：先看清要什么结果，再想怎么原地做到。

另外它有个可以顺手改掉的冗余：`Arrays.fill(copy, 0)` 是多余的，`new int[n]` 本来就全是 0
（和 0-1 背包那份里"dp 表第一行第一列不用初始化"是同一条 Java 语义）。

## 五、边界与一处不一致

```
   moveZeroes(null) -> NullPointerException     （方法里没有 null 判断）
   moveZeroes(new int[]{}) -> 两个循环都不进，什么都不做
   全零 / 全非零 -> 见第三节表格，都正确
```

`p42`、`p3` 的方法第一行都挡了 null，这份和 `p11` 没挡 —— 同一批题解里健壮程度不齐。
按 LeetCode 约定（数组长度 ≥ 1）不会触发，纯当工具方法用才需要在意。

## 六、和"交换"写法比：结果一样，写次数更少

经典替代写法是遇到非零就 `swap(nums[index], nums[i])`。实测两种写法：

```
   20,000 组随机（含 1/4 的零）：最终数组不同 —— 0 次        ← 结果完全一致
   写次数比较：交换更多 14,663 次，相等 5,337 次，覆盖更多的情况 0 次
```

具体几组（"写次数"这里统计的是**真的改变某个格的值**的次数）：

| 输入 | 覆盖写法 | 交换写法 |
| --- | --- | --- |
| `[0,1,0,3,12]` | 5 | 9 |
| `[0,0,1,2]` | 4 | 6 |
| `[2,0,1]` | 2 | 3 |
| `[1,2,3,4]` | 0 | 0 |
| `[0,0,0]` | 0 | 0 |

原因很直接：一次交换要动三个格子，而覆盖只需要"把值搬到 `index`"再"把尾巴抹成 0"，
每格至多被真正改写一次。所以两种写法**在结果上没有区别**，覆盖是写次数下界（≤ n 次有效写）。
`[1,2,3,4]` 和 `[0,0,0]` 两组是 0 —— 前者全是自写（值没变）、后者本来就全是 0，
这也说明"赋值次数"和"改变值的次数"是两个不同的口径，第三节说的是前者、这一节说的是后者，别混。

## 七、代价

```
   两趟线性扫描，写次数 = n（第二趟只写零的个数），额外空间 O(1)
```

对拍那 20,000 组是微秒级的事，所以这题真正值得记住的不是耗时，而是第二节那条不变量：

**原地压缩只有在"写指针永远不越过读指针"时才安全。** 这一条在 239 题（同一个数组上开双端队列）、
561/438 这类滑窗题里都会反复用到，值得当常识记住。

## 八、一句话记住

```
   index <= i 恒成立 → 覆盖不会踩到还没读的值，这是"能原地"的全部理由（20,000 组与额外数组版 0 差异）；
   没有零的数组会把每格都原地重写一遍（实测 4 次自写 / 长度 4），存在但无害；
   注释那份额外数组版多要 O(n) 内存、且 Arrays.fill 是多余的（new int[n] 本来就是 0），也不符合"原地"要求；
   这份没挡 null（p42/p3 挡了），同一批题解健壮性不一致。
```
