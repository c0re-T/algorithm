# LeetCode 239 滑动窗口最大值（队列里存下标而不是值，才能知道什么时候该扔）

> 对应程序：[LeetCode239_SlidingWindowMaximum.java](./LeetCode239_SlidingWindowMaximum.java)
> `main` 用 `nums = [1,3,-1,-3,5,3,6,7]`、`k = 3`，实测打印 `[3, 3, 5, 5, 6, 7]`（LeetCode 标准答案）。
> 单调递减双端队列：队头始终是当前窗口的最大值下标。

---

## 一、四步的顺序不能乱

```java
if (!deque.isEmpty() && deque.peekFirst() <= i - k) deque.pollFirst();   // 1 扔滑出窗口的
while (!deque.isEmpty() && nums[deque.peekLast()] <= nums[i]) deque.pollLast();  // 2 扔没出路的
deque.offerLast(i);                                                       // 3 自己进队
if (i >= k - 1) result[i - k + 1] = nums[deque.peekFirst()];              // 4 窗口成形后记录
```

两个设计点值得单独说：

**① 队列存的是下标，不是值。** 判"队头有没有滑出窗口"需要知道它是第几个元素，光有值判不了
（值还可能重复）。若存值就得再配一个"值→剩余出现次数"的结构，等于把下标信息重新造一遍。

**② 先扔过期、再扔被压、然后自己进队。** 这个顺序反了会怎样：把第 1 步放到第 3 步之后，
队头可能仍是过期下标却被拿去写结果 —— 因为第 4 步用的是 `peekFirst()`。

## 二、"单调"到底保证了什么

维护的不变量：**队列里的下标对应的值是严格递减的**（越靠队尾越小）。于是：

```
   新来的 nums[i] 比队尾那些都大 → 队尾那些以后永远不可能成为最大值
   （它们既比 nums[i] 小，又比 nums[i] 早滑出窗口）→ 直接扔掉是安全的
   所以每个下标最多进队一次、出队一次 → 总共 O(n) 次操作
```

逐个看他的用例（`k=3`，下面是给这份逻辑加打印后跑出来的，"扔掉的"一列区分两种丢弃方式）：

| i | nums[i] | 扔掉的 | 进队后队列（下标(值)） | 记录 |
| --- | --- | --- | --- | --- |
| 0 | 1 | — | `0(1)` | 窗口未满 |
| 1 | 3 | 压掉 `[0]` | `1(3)` | 未满 |
| 2 | −1 | — | `1(3) 2(-1)` | 队头 1 → **3** |
| 3 | −3 | — | `1(3) 2(-1) 3(-3)` | 队头 1 → **3** |
| 4 | 5 | 过期 `1`，压掉 `[3, 2]` | `4(5)` | 队头 4 → **5** |
| 5 | 3 | — | `4(5) 5(3)` | 队头 4 → **5** |
| 6 | 6 | 压掉 `[5, 4]` | `6(6)` | 队头 6 → **6** |
| 7 | 7 | 压掉 `[6]` | `7(7)` | 队头 7 → **7** |

`result = [3, 3, 5, 5, 6, 7]` ✓ 和程序输出一致。

**i=6 这一行值得看一眼**：下标 4（值 5，是上一轮的最大值）在 i=6 时**不是**被"过期"扔掉的 ——
`4 <= 6-3 = 3` 不成立；它是被新来的 6 **顺手压掉**的。也就是说第 1 步那个"过期检查"经常一轮都不生效，
真正在瘦身的是第 2 步。反过来说，如果只写第 1 步不写第 2 步，队列就会一路涨到 `k` 长度、每次都得扫一遍找最大值。

## 三、差分对拍 + 三个变体

固定种子 20,000 组随机（长度 1..30、`k` 取 1..8 且不超长度、值域 -5..5），与"每个窗口扫一遍"的暴力比：

```
   队头用 if + 队尾用 <=（他的写法）  与暴力不同 0 次
   队尾把 <= 改成 <（保留相等下标）    与暴力不同 0 次
   队头把 if  改成 while              与暴力不同 0 次
```

也就是说这三处选择**都不影响正确性**，影响的是队列长度：

```
   队列最长长度（20,000 组的平均）：<= 版 2.70，< 版 3.04
```

用 `<` 会把相等值的下标全都留在队列里，队列变长（窗口全相等时最坏能长到 `k`），但队头取最大值仍然对。
**注释里那句"一定要用 `<=`，把相等的也踢出去，避免冗余"——"避免冗余"是准确的，"一定要"则不成立**（正确性不依赖它）。

至于队头 `if` 够不够：每轮 `i` 只加 1，所以每轮最多有一个下标变成过期，而且它一定在队头
（队列下标递增）。`if` 与 `while` 因此等价 —— 上面第三行那 0 次差异就是这个论证的实测版本。

## 四、边界与一处会崩的地方

```
   k = 1            -> 就是原数组        [3,1,2] -> [3, 1, 2]
   k = n            -> 只有一个最大值    [3,1,2] -> [3]
   nums = []        -> []                （第一行 n == 0 挡了）
   k = 0            -> []                （第一行 k == 0 挡了）
   k > n（k=5, n=3）-> NegativeArraySizeException: -1
```

最后一条是真正的坑：

```java
int[] result = new int[n - k + 1];     // n=3, k=5 时长度是 -1
```

`n == 0 || k == 0` 挡不住 `k > n`。题面保证 `1 <= k <= n` 所以交上去没事，
但只要输入来自外部（比如把窗口大小做成配置项），这里就是**运行时抛 `NegativeArraySizeException`**，
而且信息只有一个 `-1`，看不出是 `k` 超了。加一句 `if (k > n) k = n;` 或者显式抛带信息的异常都要好过这个。

## 五、注释里那份"案例超时"

注释版是"每个窗口重新扫一遍"，复杂度 `O(n·k)`。实测单调队列对照它：

| n | k | 单调队列 | 每窗扫一遍 |
| --- | --- | --- | --- |
| 20,000 | 100 | 0 ms | 1 ms |
| 40,000 | 200 | 0 ms | 3 ms |
| 80,000 | 400 | 2 ms | 13 ms |
| 160,000 | 800 | 3 ms | 53 ms |
| 320,000 | 1,600 | 6 ms | **216 ms**（36 倍） |

`n·k` 到 LeetCode 这题的上限（`n = 10⁵`、`k = 10⁵` → 10¹⁰）就是"案例超时"的全部原因，注释里那句话是经验之谈且成立。
注意单调队列这一列里 `n` 从 16 万到 32 万是 3→6 ms，符合 `O(n)`；暴力的 53→216 ms 符合 `n·k`（两者都翻倍，×4）。

## 六、一句话记住

```
   队列存下标（值会重复，只有下标能判断"滑出去了"）；四步顺序：扔过期 → 扔被压 → 进队 → 记录；
   队尾用 < 还是 <= 都不影响正确性（20,000 组对拍 0 差异），只让队列从平均 2.70 变 3.04，
   注释里那句"一定要用 <="不准，"避免冗余"是对的；队头 if 与 while 等价（i 每轮只进 1）；
   k > n 会抛 NegativeArraySizeException: -1（n-k+1 是负数），n==0/k==0 挡不住它；
   注释那份 O(n·k) 实测在 n=32万/k=1600 时 216ms vs 单调队列 6ms。
```
