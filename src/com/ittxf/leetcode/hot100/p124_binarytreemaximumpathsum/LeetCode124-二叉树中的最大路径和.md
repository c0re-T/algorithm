# LeetCode 124 二叉树中的最大路径和（返回单价、更新拐点和，两件事分开）

> 对应程序：[LeetCode124_BinaryTreeMaximumPathSum.java](./LeetCode124_BinaryTreeMaximumPathSum.java)
> `main` 那棵树（根 −10，左 9，右 20，20 下面 15 和 7），实测：
>
> ```
> 最大路径和：42
> ```
>
> 42 = 15 + 20 + 7，拐点在 20，根 −10 和左边的 9 都没参与。

---

## 一、一个函数干两件事

```java
int leftGain  = Math.max(maxGain(node.left), 0);    // 负贡献当 0，不要
int rightGain = Math.max(maxGain(node.right), 0);

int priceNewPath = node.val + leftGain + rightGain; // ① 以我为拐点：左右都要
maxSum = Math.max(maxSum, priceNewPath);

return node.val + Math.max(leftGain, rightGain);    // ② 给父亲的报价：只能选一边
```

路径不能分叉，所以**交给父亲的和留在本地的必须是两个不同的数**：

- `priceNewPath` 用了左 + 右，这条路径在我这里拐弯，到此为止，不能再往上延伸；
- `return` 只带一边，因为父亲还要继续往上接，接上两条就分叉了。

把 return 写成 `node.val + leftGain + rightGain`（把拐点和当报价）实测 20,000 组里错 3,282 组。`main` 那棵树恰好测不出来 —— 它的拐点 20 就是最优解，往上没得接。

## 二、三个变体，各自错多少

20,000 棵随机树（值 −20..20），与"枚举所有简单路径"的暴力参考对比：

| 变体 | 错多少 | `main` 那棵树能测出来吗 |
| --- | --- | --- |
| 他的原版 | **0** | — |
| 去掉 `Math.max(..., 0)` 的钳位 | 6,529 / 20,000 | **测不出**（仍给 42） |
| `maxSum` 初值改成 0 | 1,637 / 20,000 | 测不出 |
| return 改成拐点和（分叉报价） | 3,282 / 20,000 | 测不出 |
| return 外面再套一层 `Math.max(0, ...)` | **0 / 20,000** | — |

第一行值得单独说：钳位的作用是"子树贡献为负就整段不要"。`main` 那棵树的左子树 9 是正贡献、根 −10 是负的但根不参与最优路径，所以删掉钳位结果照样 42。全负树 `(−2,−3,−1)` 也测不出（他的原版给 −1，删钳位也给 −1）。**要造出"负贡献被强行接上"的输入才看得见 32.6% 的错误率。**

最后一行是个反直觉的结果：给 return 也套上 `max(0, ...)` 在 20,000 组里一次都没出错。原因是父亲那边已经钳过一次了，儿子报负数上来也会被当成 0，两层钳位效果重合。它不是"必需"，但也不是"错"。

`maxSum` 初值必须是 `Integer.MIN_VALUE`：全负树 `(−2,−3,−1)` 正确答案是 −1，初值 0 会给 0（实测）。注释里已经写明了这一点。

## 三、边界

| 输入 | 输出 | 说明 |
| --- | --- | --- |
| 单节点 −3 | −3 | 正确 |
| `(−2,−3,−1)` | −1 | 正确，全负也能选出一个最大的 |
| **`null`** | **−2147483648** | `maxGain(null)` 直接返回 0，`maxSum` 从没被更新过，把初值原样吐出来 |
| 两个 `Integer.MAX_VALUE` 相连 | 2147483647 | 真值 4,294,967,294，int 溢出成 −2，被 `Math.max` 吞掉 |

空树返回 `Integer.MIN_VALUE` 而不是 0 或抛异常，是"全局变量 + 空输入"的典型后果。题面保证至少一个节点，所以不触发；但这份没有任何防护。溢出那条题面也挡住了（节点数 ≤ 3×10⁴、值域 ±1000，路径和最多 3×10⁷）。

**`maxSum` 是实例字段而且从不复位**，同一个实例按"大树 → 小树"的顺序调：

```
第1次 main树   -> 42（真值 42）
第2次 单节点5  -> 42（真值 5）
第3次 单节点-3 -> 42（真值 -3）
第4次 空树     -> 42
换新实例 单节点5 -> 5
```

`maxSum = Math.max(maxSum, ...)` 只增不减，所以第二次起返回的全是历史最大值。我一开始连着调了四次同一棵 `main` 树，得到 42 → 42 → 42 → 42，**看起来完全正常** —— 必须换一棵答案更小的树才暴露。这和 `p543` 的 `maxDiameter`、`p94` 的 `list` 是同一类隐患。

## 四、代价与递归深度

| 形状 | 节点数 | 结果 | 耗时 |
| --- | --- | --- | --- |
| 满树（高 20，全 1） | 1,048,575 | 100 | 2 ms |
| 右斜链 | 50,000 | `StackOverflowError` | — |
| 右斜链 | 100,000 | `StackOverflowError` | — |

每个节点访问一次，`O(n)` 时间、`O(h)` 栈。满树 100 万节点高度只有 20，2 ms 跑完；同样节点数换成一条链就爆栈。**风险看形状不看 n**，和 `p104` 完全一致。

## 五、一句话记住

```
   priceNewPath = 我 + 左 + 右（拐点，就地更新 maxSum）；
   return       = 我 + max(左, 右)（报价，只能一边，否则分叉）；
   两个都套 max(...,0) 钳位，maxSum 初值 Integer.MIN_VALUE；
   20,000 组与枚举所有路径 0 差异；三个变体分别错 6,529 / 1,637 / 3,282 组，
   而 main 那棵树一个都测不出来；
   null 返回 −2147483648（初值原样吐出）；
   maxSum 是实例字段不复位：大树之后调单节点 5 仍返回 42（连调同一棵树测不出来）；
   满树 100 万节点 2 ms，5 万节点的斜链爆栈。
```
