# LeetCode 1 两数之和（`put` 写在 `if` 后面不是随手放的，是全部正确性的来源）

> 对应程序：[LeetCode1_TwoSum.java](./LeetCode1_TwoSum.java)
> 一次扫 + 一张哈希表：走到 `nums[i]` 时，不去问"后面有没有配我的"，而是问"**我要的补数前面对不对上过**"。
> 题面保证**恰好一组解**，所以拿到第一组就直接返回。

---

## 一、`main` 里那次调用，逐轮走一遍

`twoSum(new int[]{2,7,11,15}, 9)` → 实测打印 `[0, 1]`：

| i | `nums[i]` | `complement = 9 - nums[i]` | map 里有吗 | 动作 | 之后 map |
| --- | --- | --- | --- | --- | --- |
| 0 | 2 | 7 | 无 | `put(2, 0)` | {2=0} |
| 1 | 7 | 2 | **有（下标 0）** | `return {0, 1}` | — |

返回 `{map.get(complement), i}` —— **先放补数的下标、再放当前的下标**，所以答案天然是升序的（`[0,1]` 而不是 `[1,0]`）。

## 二、`containsKey` 在 `put` 之前：这一句顺序就是"不许自己配自己"

```java
if (map.containsKey(complement)) { return ...; }   // 先查
map.put(nums[i], i);                              // 再存
```

把两句调换（先存再查），实测：

| nums | target | 先查再存（他的写法） | 先存再查 | 暴力穷举的第一个解 |
| --- | --- | --- | --- | --- |
| `[3,3]` | 6 | `[0, 1]` ✓ | **`[0, 0]`** ✗ | `[0, 1]` |
| `[1,1,1]` | 2 | `[0, 1]` ✓ | **`[0, 0]`** ✗ | `[0, 1]` |
| `[4,4]` | 8 | `[0, 1]` ✓ | **`[0, 0]`** ✗ | `[0, 1]` |
| `[3]`（只有一个 3） | 6 | `[]` ✓（无解） | **`[0, 0]`** ✗（把同一个元素用了两次） | `[]` |

**"先存再查"会让每个元素都和自己配成一对** —— 因为查的那一刻，`nums[i]` 已经躺在表里了。
只有当 `2 * nums[i] == target` 时才暴露，所以拿 `[2,7,11,15]` 这种没有重复、也没有半值的用例去测，**完全测不出来**。
这也是这份代码里最值得记的一处：**算法的正确性挂在两句代码的先后顺序上，而它看起来只是风格问题。**

## 三、同一个值只留最后一个下标 → 解不唯一时返回哪一对由覆盖决定

`map.put(nums[i], i)` 对重复值会**覆盖**旧下标。所以：

```
nums = [2, 2, 4, 4], target = 6
  他的写法    -> [1, 2]     （值 2 在表里的下标已被覆盖成 1）
  暴力第一个  -> [0, 2]
```

规模化测一遍：固定种子造 60,000 组小值域（0..5，长度 2..9）的数组，只统计"确实有解"的例子，
比较他的返回和暴力**第一个**解：**8,581 次不一致**，且这些不一致全部是"另一组合法配对"（没有一例加和不对）。

**LeetCode 不要求第几组，所以这不是 bug**，但要知道两件事：
返回值不保证是最靠前的那一对；如果哪天题目改成"返回所有解"或"字典序最小"，这张覆盖式的表就得换成 `Map<Integer, List<Integer>>`。

## 四、和暴力穷举对拍：120,000 组，四类失败全 0

随机 120,000 组（数组长度 1..12、值域 -3..7、target -5..9，故意留大量无解与重复）：

```
答案加和不对        ：0
自己配自己          ：0
有解却返回空数组    ：0
无解却返回了东西    ：0
```

## 五、无解时返回 `new int[0]`：打印是 `[]`，按长度 2 去取得崩

```
   twoSum([2,7,11,15], 100) -> []   length = 0
   调用方若按「一定有解」写 res[0] -> ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0
```

按题面（保证恰好一组解）这条路走不到，所以返回空数组是可以的、也符合平台对"无解"的表示。
但**当工具方法用**就有个约定问题：调用方分不清"长度为 0 的无解"和"我自己忘了判断长度"，
要么抛带信息的异常，要么返回 `Optional`。顺带：注释里那句"返回一个长度为 0 的数组，表示没有找到"就是这个约定，
写清楚了 ✓ —— 只是 `main` 里没演示这条分支。

## 六、`target - nums[i]` 会不会溢出

纯算式实测：

```
Integer.MIN_VALUE - 1  =  2147483647     （绕回正数）
Integer.MAX_VALUE - (-1) = -2147483648   （真实是 2147483648，绕成负数）
```

所以这个减法**是会溢出的**，只是题面把范围卡住了：`nums[i]` 和 `target` 都在 ±10⁹，
`target - nums[i]` 的绝对值最大 2×10⁹，而 `Integer.MAX_VALUE = 2,147,483,648` —— **有解，但只剩约 7% 余量**。
把题面换成"±10¹⁸ 的 long"或者自己拿它做通用工具时，就得改成 `long complement = (long) target - nums[i]`。

（对照：二分查找笔记第九节的 `(left+right)/2` 是同一种坑，那边在 Java 里几乎踩不到，这边靠题面数据范围挡住。）

## 七、代价：一遍扫 vs 双重循环

实测（构造 `nums[i] = 2i`，把解放在最后，逼暴力走满 `n²/2` 次比较）：

| n | 哈希一遍扫 | 暴力两重循环 |
| --- | --- | --- |
| 2,000 | 0 ms | 0 ms |
| 20,000 | 2 ms | **38 ms** |
| 200,000 | 8 ms | （要 200 亿次比较，没跑） |
| 2,000,000 | 135 ms | （要 2 万亿次比较，没跑） |

n 从 2 千到 2 万（×10），暴力从 0ms 跳到 38ms（×100，平方律），哈希是 0ms→2ms（×10 且被常数吃掉）。

代码里注释掉的那份两重循环还有个容易被忽略的行为：**它不 `break`，`res` 会被覆盖到最后一个匹配**，
所以它返回的是"最后一组解"而不是第一组（实测）：

```
nums=[2,2,4,4] target=6 : 暴力第一个 [0,2] | 注释那份返回 [1,3]
nums=[1,1,1,5] target=2 : 暴力第一个 [0,1] | 注释那份返回 [1,2]
```

想拿它当"暴力对照实现"来验证哈希版，得先补上 `return`，否则两边比的是不同的解。

## 八、`containsKey` + `get` 两次哈希查找值不值得改

理论上 `map.containsKey(c)` 紧跟 `map.get(c)` 会把同一个桶查两遍，改成一次 `Integer v = map.get(c); if (v != null) ...` 更省。
实测 200 万元素、解在中段：

```
   第一轮：containsKey+get 7 ms | 只用 get 7 ms
   第二轮：containsKey+get 5 ms | 只用 get 4 ms
```

**差别落在噪声里**（第二轮才是热身后稳态，省了 1ms / 20%）。所以这一处属于"可以改、但别当成性能优化"的级别 ——
真要论收益，`v != null` 还顺手避开了"值可以是 null"的语义坑（这张表不会存 null，所以两种写法都安全）。
对照 49 题那边 `computeIfAbsent` 的实测收益就有 1.4 倍（见那篇笔记第六节）。

## 九、一句话记住

```
   把"找一对"换成"找补数"，一遍扫 + 一张表就是 O(n)；
   先 containsKey 再 put —— 这个顺序是"不用同一个元素配自己"的唯一保证，
   调换之后 [3,3]/6 会返回 [0,0]，而题面示例 [2,7,11,15] 恰好测不出来；
   同一个值只留最后一个下标，所以解不唯一时返回的不是最靠前那一对（实测 60,000 组里 8,581 次不同，全部合法）；
   无解返回空数组要靠 length 判断；target - nums[i] 在题面 ±1e9 下不溢出，但只剩 7% 余量。
```
