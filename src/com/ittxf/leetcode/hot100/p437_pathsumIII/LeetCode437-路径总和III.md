# LeetCode 437 路径总和 III（前缀和 + 回溯，map 里只能有当前这条路径）

> 对应程序：[LeetCode437_PathSumIII.java](./LeetCode437_PathSumIII.java)
> `main` 那棵 9 节点树，targetSum=8，实测：
>

> 算路径和为8的路径个数: 3
> ```
>
> 三条是 `5→3`、`5→2→1`、`−3→11`。路径必须**向下**（父到子），但不必从根开始、也不必到叶子结束。

## 一、把 `p560` 的前缀和搬到树上

数组版（`p560`）的结论是：子数组和为 k ⟺ 存在两个前缀和之差为 k。树上也一样，只不过"前缀"变成了**从根到当前节点这条路径**：

```java
curSum += node.val;                                              // 1. 根到我的前缀和
int count = prefixSumMap.getOrDefault(curSum - targetSum, 0);    // 2. 查有多少个祖先满足差值
prefixSumMap.put(curSum, prefixSumMap.getOrDefault(curSum, 0) + 1); // 3. 把自己登记进去
count += dfs(node.left, curSum, targetSum, prefixSumMap);        // 4. 往下走
count += dfs(node.right, curSum, targetSum, prefixSumMap);
prefixSumMap.put(curSum, prefixSumMap.get(curSum) - 1);          // 5. 回溯：把自己撤掉
```

第 2 步累加的是**次数**不是 1：同一个前缀和可能在路径上出现多次（有 0 或负数时完全可能），每一次都对应一条不同的路径。

`put(0L, 1)` 是空前缀，代表"从根开始的那一段"。删掉它实测 20,000 组里错 7,115 组，最小反例：根 1、孩子 2，target=1 —— 真值 1（根自己就是一条），不预置给 0。

## 二、第 5 步回溯是这份代码的命门

数组版的前缀和表是"整条扫描线"共享的，树上的表必须**只装当前这条根到节点的路径**。走完左子树要去右子树时，左子树的前缀和必须撤掉，否则右子树会查到左边的祖先。

删掉第 5 步实测：

```
20,000 组差异 = 9,798（49.0%）
最小反例：根 1、左 4、右 5，target = 1
          真值 1（只有根自己），删回溯给 2
```

多出来的那条是这么来的：走完左子树后 map 里留下前缀和 `1+4=5`；到右节点 5 时 `curSum = 1+5 = 6`，查 `6 - 1 = 5` 命中 —— 命中的是**左子树留下的**前缀和，而 4 和 5 是兄弟，根本不在同一条向下路径上。

回溯写成 `put(curSum, count - 1)` 而不是 `remove(curSum)`，实测示例树跑完后 map 里还剩 8 个 key，其中 7 个计数为 0。这**不影响正确性**：`getOrDefault` 命中一个 0 也只是加 0。代价是表会留着所有出现过的前缀和（最坏 O(n) 个 key 而不是 O(h)），但题面 n ≤ 1000 无所谓。

## 三、随机对拍与实例字段

20,000 棵随机树（值 −5..5，允许负数和 0），与注释里那份"每个节点当起点重走一遍"的暴力对比：

```
差异 = 0
```

注释那份是 `O(n²)`（每个起点各走一次子树），但思路直白，正好当参考。

`prefixSumMap` 是 `pathSum` 里的**局部变量**，每次调用新建。同一个实例连调三次：3, 3, 1 —— 第三次换了 target 就是新答案，**没有 `p94`/`p124`/`p543` 那种字段泄漏**。这是这份实现值得学的一点：需要跨递归层共享的状态用参数传，不要图省事放字段。

## 四、为什么用 long

`curSum` 和 map 的 key 都是 `long`，`targetSum` 也转成 long。实测三个 `2^30` 连成一条链、target = `−2^30`：

```
他用 long      -> 0（正确：全正数不可能凑出负 target）
改成 int 前缀和 -> 1（凭空多算一条）
```

原因是 `3 × 2^30 = 3,221,225,472` 溢出 int 之后正好等于 `−2^30`，于是第三个节点上 `curSum - targetSum = 0`，命中了预置的空前缀。题面 `|val| ≤ 1000`、`n ≤ 3000`，前缀和最多 3×10⁶，int 绰绰有余 —— **long 在这里是防御性的，不是必需的**，但它让"前缀和"这个概念不用担心值域，写起来更省心。

## 五、代价与递归深度

| 形状 | 节点数 | 他的前缀和版 | 注释里的暴力版 |
| --- | --- | --- | --- |
| 满树（高 18，全 1） | 262,143 | **3 ms** | 6 ms |
| 满树（高 20，全 1） | 1,048,575 | **12 ms** | 29 ms |
| 右斜链 | 50,000 / 100,000 | `StackOverflowError` | — |

两档都只快 2 倍多，比"O(n) 对 O(n²)"给人的预期小得多。原因是**满树上暴力根本不是 O(n²)**：每个起点只能往自己的子树里走，全部起点加起来是 `O(n·h)`，而满树的 h 只有 18/20。真正让暴力退化成 `O(n²)` 的是斜链（每个起点都能走到底），而斜链这份又爆栈。

所以这组数字的正确读法是：前缀和版在满树上稳定快 2 倍多，代价是每节点两次 HashMap 查询加两次 put；它的渐近优势要在**深树**上才完全兑现，而深树恰好是它栈撑不住的地方。
