# LeetCode 21 合并两个有序链表（dummy + 摘链，不新建节点）

> 对应程序：[LeetCode21_MergeTwoSortedLists.java](./LeetCode21_MergeTwoSortedLists.java)
> `main` 合并 `1 -> 2 -> 4` 与 `1 -> 3 -> 4`，实测：
>
> ```
> 合并后的链表: 1 -> 1 -> 2 -> 3 -> 4 -> 4
> ```

---

## 一、这趟循环只做一件事：摘一个节点接到尾巴

```java
while (list1 != null && list2 != null) {
    if (list1.val < list2.val) { current.next = list1; list1 = list1.next; }
    else                       { current.next = list2; list2 = list2.next; }
    current = current.next;
}
current.next = list1 != null ? list1 : list2;
```

`current.next = listX` 改的是**原链表节点的 `next`**，没有 `new ListNode`。所以输出链表是两条输入链表"拆开再串起来"的结果。

剩下一整条不需要再逐个摘：它已经有序，直接挂到尾巴上。

## 二、`<` 而不是 `<=`：相等时先取右边

实测两个值都为 1 的单节点：

```
输出首节点来自 list2（< 号导致相等取右边）
```

两种写法结果都是合法有序链表，区别只在"相等元素谁在前"。如果要求**稳定**（保持 list1 的元素在前的相对次序），这里应该写 `<=`；LeetCode 不检查这一点。

## 三、节点复用与"入参被拆开"

6 个输入节点，输出仍是这 6 个：

```
输出 6 个节点，来自输入链表 6 个（6/6 表示零新建）
```

代价是调用方的链表结构被改写。实测合并 `[1,10,11]` 与 `[2,3]` 之后，从原 list1 的头出发：

```
[1, 2, 3, 10, 11]
```

原来的 `1 -> 10 -> 11` 已经不存在了 —— `1.next` 被改成 2，`3.next` 被改成 10。**返回值是唯一正确的入口**，原头指针只能当"某个节点的引用"用。

空链表组合也覆盖了：

```
null + null -> null
null + [1,2] -> [1,2]     ← 直接返回 list2，连 dummy 都没用上
[1,2] + null -> [1,2]
```

## 四、差分对拍与代价

两边各 0..30 个节点、值域 0..9（故意制造大量相等），固定种子 20,000 组，与"拼起来再 `Arrays.sort`"对比：

```
不一致 = 0
```

50 万 + 50 万（奇偶交错、共 999,999 个节点）合并：**3.8 ms**。每个节点只被摘一次，`O(m+n)` 时间、`O(1)` 额外空间（结果复用原节点）。

## 五、和 23 / 148 的关系

| 程序 | 复用的部分 | 新增的东西 |
| --- | --- | --- |
| 21 | `merge` 本体 | dummy + 摘链 |
| 23 | 直接调用同样的 `merge` | 外层"先并第一个、再并下一个"的顺序 |
| 148 | 同样的 `merge` | 快慢指针找中点 + 递归排序两半 |

`merge` 是这三道题共同的地基。23 的性能问题（顺序合并 `O(k²n)`）就出在外层调用顺序上，不在 `merge` 本身。

## 六、一句话记住

```
   dummy 当假头，while 两条都不空就摘较小的那个接到尾巴，剩一条整段挂上；
   < 相等取右边（要稳定就写 <=）；
   全程不 new 节点，输出就是入参节点重排 —— 原链表结构会被拆掉；
   20,000 组（大量重复值）0 差异；100 万节点 3.8 ms，O(m+n)/O(1)。
```
