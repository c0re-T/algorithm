# LeetCode 42 接雨水（`leftMax < rightMax` 这一步为什么能决定"现在就能结算"）

> 对应程序：[LeetCode42_TrappingRainWater.java](./LeetCode42_TrappingRainWater.java)
> `main` 用 `[0,1,0,2,1,0,1,3,2,1,2,1]`，实测打印 `6`（LeetCode 标准答案）。
> 双指针 + 两个"我这一侧见过的最高柱子"，每步只结算**较矮那一侧**当前格子的水量。

---

## 一、核心那句判断在担保什么

```java
leftMax = Math.max(leftMax, height[left]);
rightMax = Math.max(rightMax, height[right]);
if (leftMax < rightMax) { water += leftMax - height[left]; left++; }
else                    { water += rightMax - height[right]; right--; }
```

第 i 格能接多少水 = `min(左边最高, 右边最高) - height[i]`。难点在于"另一边的最高"我们还没扫到。
这一行的用处就是把它绕开：

```
   当 leftMax < rightMax 时，说明「rightMax 已经比 leftMax 高了」，
   而真正的右边最高只可能 ≥ rightMax（后面还有更高的），
   ⇒ min(真左高, 真右高) 一定就等于 leftMax，左指针这一格的水可以直接结算，不用再等
```

反过来（`rightMax <= leftMax`）就结算右边那一格。**每一步都恰好有一侧是"已经能确定的"**，
所以 `left`/`right` 各走一趟就够，`O(n)` 时间、`O(1)` 空间。

对比最朴素的"逐列看左右最高"（`O(n²)` 时间）和"预存两个数组"（`O(n)` 时间但 `O(n)` 空间），
双指针版本省掉的正是那两个数组 —— 代价是那份"哪一侧已经确定"的推理，不好想但一旦想通就最短。

## 二、和逐列暴力对拍

固定种子 20,000 组随机（长度 2..15、高度 0..7），与"每一格现场扫左右最高"的暴力比：**不同 0 次**。

顺手测了那句判断的两个分支写法：把 `leftMax < rightMax` 改成 `leftMax <= rightMax`（相等时改走左支），
20,000 组**也全部相同**。原因是相等时 `leftMax - height[left]` 和 `rightMax - height[right]` 都是合法的结算值，
先算哪一边都不影响最终总和 —— 和 p11 那道"相等走哪支"的结论是同一件事。

## 三、边界实测

| height | 返回 | 说明 |
| --- | --- | --- |
| `null` | 0 | 方法第一行挡了 null |
| `[]` | 0 | `length <= 2` 直接返回 |
| `[5]` | 0 | 同上 |
| `[5,5]` | 0 | 两格接不住水 |
| `[0,0]` | 0 | 没有墙 |
| `[5,1,5]` | **4** | 中间那格 5-1 |
| `[2,0,2]` | **2** | 中间那格 2-0 |

`length <= 2` 这一条不是可有可无的形式检查：只有两根柱子时中间没有格子，但如果去掉这条判断，
循环会走进 `left < right` 的分支并做 `water += leftMax - height[...]` —— 恰好还是 0（因为结算的那格自己就是墙）。
所以真正起作用的是"`left++`/`right--` 之前那一格必定已经算过"，两格的情况无论走哪支都不加钱。**留着这句判断是对的，理由却和直觉不同。**

## 四、真实逐轮打点

`[0,1,0,2,1,0,1,3,2,1,2,1]`（下标 0..11）。给同一份逻辑加上打印后跑出来的全部 11 轮：

| 轮 | 之后 left | 之后 right | leftMax | rightMax | 走哪支 | 结算哪格 | 加的水 | 累计 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 1 | 11 | 0 | 1 | 左支 | 下标 0 | 0 | 0 |
| 2 | 1 | 10 | 1 | 1 | 右支 | 下标 11 | 0 | 0 |
| 3 | 2 | 10 | 1 | 2 | 左支 | 下标 1 | 0 | 0 |
| 4 | 3 | 10 | 1 | 2 | 左支 | 下标 2 | **1** | 1 |
| 5 | 3 | 9 | 2 | 2 | 右支 | 下标 10 | 0 | 1 |
| 6 | 3 | 8 | 2 | 2 | 右支 | 下标 9 | **1** | 2 |
| 7 | 3 | 7 | 2 | 2 | 右支 | 下标 8 | 0 | 2 |
| 8 | 4 | 7 | 2 | 3 | 左支 | 下标 3 | 0 | 2 |
| 9 | 5 | 7 | 2 | 3 | 左支 | 下标 4 | **1** | 3 |
| 10 | 6 | 7 | 2 | 3 | 左支 | 下标 5 | **2** | 5 |
| 11 | 7 | 7 | 2 | 3 | 左支 | 下标 6 | **1** | **6** |

11 轮 = 12 格 − 1，`left == right == 7` 时退出，每轮恰好结算一格。
各格贡献 `下标2=1、4=1、5=2、6=1、9=1`，合计 **6** ✓ 与"逐列取 min(左高,右高) 减自己"的暴力一致。

三处值得注意：

- **结算顺序不是从左到右**：下标 11、10、9、8 先被右支结掉，下标 0、1、2 又被左支结掉，最后才轮到中间的 3..6。
  谁先算取决于当时 `leftMax` 和 `rightMax` 谁小，跟格子在原数组里的位置无关。
- **下标 3（高度 2）在第 8 轮结算时加 0** —— 那一刻它就是当前的左墙，本来就不该有水。
- 第 2 轮 `leftMax == rightMax == 1` 走的是 `else`（右支），这正是第二节里"`<` 换成 `<=` 也不变"的那一类相等分支。

（这一节我最初是手推的，多算了一格 —— 程序打点才是凭据。这类"逐轮表"恰好是最容易自己骗自己的地方，
所以凡是表格里有具体数字的，都来自加打印跑一遍。）

## 五、代价

| n | 双指针 | 逐列暴力 |
| --- | --- | --- |
| 2,000 | 0 ms | 2 ms |
| 4,000 | 0 ms | 6 ms |
| 8,000 | 0 ms | 28 ms |
| 16,000 | 0 ms | **111 ms** |

暴力的 `n²` 曲线（2→6→28→111，n 翻倍时间约 ×4）非常干净；双指针全程读 0 ms。
LeetCode 上这题 n ≤ 2×10⁴，暴力和双指针都能过，但**单调栈解法（另一种经典写法）和这份双指针在同一个量级**，
差别在"按列结算"还是"按凹槽结算"，可以拿来对照着理解"水到底是怎么被围出来的"。

## 六、一句话记住

```
   第 i 格的水 = min(左最高, 右最高) - height[i]，而 min 里"没扫到的那一侧"由另一根指针上已经看到的更高柱子担保；
   leftMax < rightMax 时结算左格、否则结算右格 —— 每一步都恰好有一侧已经能定案，所以 O(n) 时间 O(1) 空间；
   20,000 组随机与逐列暴力 0 差异，把 < 换成 <= 也 0 差异；
   这份有 null 判断（同批的 p11 / p283 没有）；length <= 2 提前返回留着是对的；
   手工逐轮推演这次多算了 1，别把笔记里的逐轮表当凭据 —— 能当凭据的是对拍。
```
