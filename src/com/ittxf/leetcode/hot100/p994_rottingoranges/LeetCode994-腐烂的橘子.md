# LeetCode 994 腐烂的橘子（多源 BFS，一层就是一分钟）

> 对应程序：[LeetCode994_RottingOranges.java](./LeetCode994_RottingOranges.java)
> `main` 那张 `{{2,1,1},{1,1,0},{0,1,1}}`，实测：
>
> ```
> 4
> ```

---

## 一、一分钟 = 队列里的一整层

初始化时把**所有**腐烂橘子一次性塞进队列，它们就成了同一层的起点，之后每轮 `while` 向外推一层：

```java
if (grid[i][j] == 2) queue.offer(new int[]{i, j});
else if (grid[i][j] == 1) freshCount++;
```

`main` 的用例只有一个源，逐分钟打点是这样：

```
初始: 队列 1 个源, freshCount = 6
第 1 分钟: 取出 1 个, 新腐烂 (1,0) (0,1), freshCount = 4, 队列剩 2
第 2 分钟: 取出 2 个, 新腐烂 (1,1) (0,2), freshCount = 2, 队列剩 2
第 3 分钟: 取出 2 个, 新腐烂 (2,1),         freshCount = 1, 队列剩 1
第 4 分钟: 取出 1 个, 新腐烂 (2,2),         freshCount = 0, 队列剩 1   ← 注意这里
返回 4
```

最后一行是重点：**`freshCount` 已经归零，队列里却还剩一个格子**（第 4 分钟刚腐烂的 `(2,2)`，它本来要在第 5 分钟去感染别人，但已经没人在等它了）。`while` 条件里那个 `freshCount > 0` 就是为了在这一刻立刻停住。

多源同时扩散这件事 `main` 测不出来（只有一个源），是靠第八节那 20,000 组随机网格确认的 —— 那些网格里 30% 的格子是腐烂源。

## 二、`int size = queue.size()`：冻结的是"层"，不是"队列"

```java
int size = queue.size();          // 只读一次
for (int k = 0; k < size; k++) { ... queue.offer(...); }
```

循环体里 `offer` 进来的新格子属于**下一分钟**，所以不能算进这一轮的 `size`。写成 `for (int k = 0; k < queue.size(); k++)` 每次判断都重新读，就同时踩两个坑：

- **偏小**：新入队的格子被当成本分钟的继续处理，一分钟扩散了不止一层。`{{2,1},{1,1}}` 原版 2 分钟，实时读只给 **1**。
- **偏大**：`poll` 让 `size` 变小、`k` 变大，两头往中间挤，**初始层里靠后的源根本没轮到就被挤出去了**，推迟到下一分钟。`{{2,2,1}}` 原版 1 分钟，实时读给 **2** —— 队列里本来有两个源，`k=0` 取走一个之后 `size` 变成 1，`k=1` 时 `1 < 1` 不成立，第二个源这一分钟压根没处理。

穷举 1×1 到 3×3 的全部 3 进制网格（共 21,297 组）：

```
1×1 / 1×2 / 2×1  差异 0
1×3              差异 1     首例 [[2,2,1]]       原版 1  实时读 2
2×2              差异 8     偏小 4 / 偏大 4
2×3              差异 129
3×2              差异 134
3×3              差异 5318
合计 5,591 组不一致（26.25%），其中偏小 1,003、偏大 4,588
```

**最短反例只有 3 个格子**（`1×3` 或 `3×1` 的 `[[2,2,1]]`）。而 `main` 的用例上实时读给出的也是 4 —— 光跑 `main` 永远发现不了。20,000 组随机网格里它错 6,148 组。

## 三、`freshCount > 0`：少一个条件就多一分钟

把 `while (!queue.isEmpty() && freshCount > 0)` 改成只判 `!queue.isEmpty()`，`main` 的用例从 4 变成 **5**。原因就是第一节最后那行：第 4 分钟结束时队列还剩 1 个，于是又进一轮 `minutes++`，这一轮一个橘子都没感染，把队列 poll 空了才退出 —— 白算一分钟。

20,000 组随机网格的差值分布干净得出奇：

```
答案为 0 / -1 的 5,575 组：全部不受影响
答案为正数的 14,425 组：全部出错，且差值恰好都是 +1（+0=0  +1=14425  +2=0  +3=0）
```

两类不受影响各有原因：答案是 0 的走的是循环前那句 `return 0`，根本没进 `while`；答案是 −1 的靠"队列空了"退出，`freshCount` 那个条件从头到尾没起过作用。**只有"感染完了但队列还有剩"这一种收尾会多算一轮**，而它恰好等价于"答案是正数"。

## 四、`grid[newI][newJ] = 2` 管的是正确性，不是终止

直觉上"不标记 visited 会死循环"，实测**不会**：

| 用例 | 返回值 | poll 次数 | freshCount 变化 |
| --- | --- | --- | --- |
| `main` 的例子 | −1 | 6 | 6 → **−6** |
| 50×50 全新鲜 + 一个源 | −1 | 721 | 2,499 → **−87** |

不写 `grid[newI][newJ] = 2`，同一个新鲜格子会被不同邻居反复感染，`freshCount--` 一路减成负数，`freshCount > 0` 不成立就退出了，最后 `freshCount == 0` 也不成立 → 返回 −1。2,500 格的网格只 poll 了 721 次就结束，离死循环差得远。

所以这行标记的职责是**防止重复计数**（visited），真正拦住循环的是 `freshCount` 冲过零点变成负数。它删掉之后返回 −1 是"算错了"，不是"卡住了" —— 这两件事排查方向完全不同。

## 五、两处实测等价的写法（别当成 bug 去修）

| 改动 | `main` | `{{0,2}}` | 20,000 组差异 |
| --- | --- | --- | --- |
| 删掉 `if (freshCount == 0) return 0;` | 4 | 0 | **0** |
| `minutes++` 从内层 `for` 之前挪到之后 | 4 | — | **0** |

- 提前 `return` 是**冗余的**：没有新鲜橘子时 `while` 的 `freshCount > 0` 直接挡住，一轮都不进，`minutes` 保持 0，末尾 `freshCount == 0` 成立照样返回 0。它省的只是建 `directions` 数组和一次条件判断。
- `minutes++` 前后等价：每执行一轮就恰好加一次，两种放法都数到同一轮。唯一可能出岔子是"感染了 0 个的一轮"，但那种轮次必然把队列 poll 空（没有新 `offer`），紧接着就退出循环返回 −1，`minutes` 是多少根本不影响结果。

记在这里是为了以后别"顺手优化"其中一处、又以为另一处才是关键。真正的关键是第二节那个冻结的 `size` 和第三节那个 `freshCount > 0`。

## 六、边界与异常

| 输入 | 结果 |
| --- | --- |
| `{{0}}` / `{{2}}` / `{{0,2}}`（官方例 3） | 0 |
| `{{1}}` | −1 |
| `{{1,2}}` | 1 |
| 全新鲜 `{{1,1},{1,1}}` | −1 |
| 孤岛 `{{2,0},{0,1}}` | −1 |
| 官方例 2 `{{2,1,1},{0,1,1},{1,0,1}}` | −1 |
| `new int[1][0]` / `new int[3][0]`（有行没列） | 0 |
| **`new int[0][]` / `new int[0][0]`** | `ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0` |
| `null` | `NullPointerException: Cannot read the array length because "<parameter1>" is null` |
| 含非法值 `{{2,3},{1,1}}` | 2（`3` 被当成空格） |

空网格崩在第二行 `int cols = grid[0].length;` —— 无条件读第 0 行。同层的 `p200` 开头有 `grid.length == 0` 挡一层（那份 `null` 和空网格都给 0），这份连那一层都没有。题面保证 `1 <= m, n <= 10`，线上不触发。

非法值那条：初始化只认 `== 2` 和 `== 1`，其余一律当空格，所以传进来个 `3` 既不腐烂也不新鲜，等同 `0`。

**锯齿矩阵有两种命运**，取决于第 0 行是长还是短（参考实现按每行自己的长度算）：

| 输入 | 他的结果 | 逐行参考 |
| --- | --- | --- |
| `{{2,1},{1}}` | AIOOBE `Index 1 out of bounds for length 1` | 1 |
| `{{2,1,1},{1,1}}` | AIOOBE `Index 2 out of bounds for length 2` | 2 |
| `{{1,1},{2}}` | AIOOBE `Index 1 out of bounds for length 1` | 2 |
| `{{2},{1,1}}` | **1** | 2 |
| `{{2,1},{1,1,1}}` | **2** | 3 |

第 0 行比后面某行**长** → 越界崩；第 0 行比后面**短** → 多出来的列被静默忽略（初始化按 `cols` 扫不到，扩散时 `newJ < cols` 也挡着），不报错、答案偏小。后一种更难发现。

## 七、入参被就地改写

`grid[newI][newJ] = 2` 写的是传进来的那个数组。同一份网格连调两次：

```
调用前 fresh = 6
第一次 = 4, 调用后 fresh = 0
第二次（同一份）= 0
调用后矩阵:
  [2, 2, 2]
  [2, 2, 0]
  [0, 2, 2]
```

和 `p200` 的淹没式 DFS 是同一类副作用：不报错，第二次的 0 看着还很"合理"（"橘子都烂完了当然是 0 分钟"）。注释里写了"标记为腐烂"，但没说标记的是调用方的地图。要复用就得自己先拷贝。

## 八、20,000 组随机对拍

随机 1..6 × 1..6 网格，每格 20% 空格 / 50% 新鲜 / 30% 腐烂，种子 20261109。答案分布：−1 有 4,731 组、0 有 844 组、正数 14,425 组。

参考实现走的是完全不同的路子 —— **逐分钟全图扫描**：每分钟扫一遍整张图，把所有"紧邻腐烂橘子的新鲜格子"收集到一个列表里，扫完之后一次性一起改成腐烂。不用队列，也天然就是多源同时扩散。

```
原版 vs 逐分钟扫描参考: 差异 = 0
```

各变体在同一批数据上的表现：

| 写法 | 出错组数 | `main` 用例 |
| --- | --- | --- |
| 原版 | **0** | 4 |
| `while` 去掉 `freshCount > 0` | 14,425 | 5 |
| `for` 实时读 `queue.size()` | 6,148 | 4（测不出来） |
| 四个方向改成八个（含对角线） | 8,737 | 2 |
| 删 `freshCount--` | 14,425 | −1 |
| 删 `if (freshCount == 0) return 0;` | 0 | 4 |
| `minutes++` 后置 | 0 | 4 |

八连通的首例是 `[[1,1],[2,1],[0,1],[1,0],[1,1]]`：原版 −1，变体 3 —— 对角线把 `(2,1)` 和 `(3,0)` 连上了，本来被两个 `0` 隔开的孤岛不再孤立。题面是四连通，这份写对了。

删 `freshCount--` 错的也恰好是那 14,425 组正数用例：计数永不归零，`while` 只能靠队列空退出，末尾判定失败一律返回 −1。

## 九、BFS 不吃栈：和递归 DFS 的对照

这份用队列，栈深度恒为 1。为了量出差距另写了一份**分钟松弛式递归 DFS**（`dfs(i, j, minute)`：若 `minute` 比格子上记录的时间早就更新并往四周递归）当对照 —— 注意它和 `p200` 那份纯淹没式 DFS 不是同一份代码，两边的爆栈线不能直接互相比。

| 形状 | 陆地格数 | 他的 BFS | 递归 DFS |
| --- | --- | --- | --- |
| 蛇形 20×20 | 210 | 209 分钟 / 5 ms | 209 |
| 蛇形 40×40 | 820 | 819 / 0 ms | 819 |
| 蛇形 100×100 | 5,050 | 5,049 / 1 ms | 5,049 |
| **蛇形 140×140** | **9,870** | **9,869 / 0 ms** | **`StackOverflowError`** |
| 蛇形 200×200 | 20,100 | 20,099 / 1 ms | `StackOverflowError` |
| 全 1 方阵 110×110 | 12,100 | 218 / 1 ms | 218 |
| 全 1 方阵 200×200 | 40,000 | 398 / 0 ms | `StackOverflowError` |
| 全 1 方阵 300×300 | 90,000 | 598 / 1 ms | `StackOverflowError` |

蛇形那组第一次量错了：奇数行的连接格全放在同一列，造出来的是"梯子"不是单条长路径，到处是捷径，递归深度只有 596，看着像"递归也扛得住"。把连接列改成逐行交替左右之后，深度才真的等于陆地格数减一，140×140 就倒。**和 `p98` 那次一样：要量递归深度，输入必须能让递归一路跑到底。**

规模与耗时（全新鲜 + 角上一个源，答案 = `rows + cols - 2`）：

```
100x100    ->  198 分钟,  0 ms
300x300    ->  598 分钟,  1 ms
500x500    ->  998 分钟,  4 ms
1000x1000  -> 1998 分钟, 19 ms（复测 16 ms）
```

一百万格 19 ms，每格只入队一次，`O(m·n)` 没有退化。题面 `m, n ≤ 10`，量到 1000×1000 只是为了确认这一点。

队列峰值也不是 `O(m·n)`：300×300 中心放一个源，300 分钟，**队列里最多同时只有 598 个格子** —— 约等于菱形波前的周长（2×边长），不是整张图。

## 十、一句话记住

```
   所有腐烂源一次性入队 = 同一层，每轮 while 推一层就是一分钟；
   int size = queue.size() 必须冻结：实时读会同时偏小（一分钟走了多层）和偏大（poll 与 k 两头挤，初始层靠后的源没轮到），
     最短反例 3 个格子 [[2,2,1]] 原版 1 / 实时读 2，穷举 21,297 组错 5,591 组，而 main 上两者都给 4；
   freshCount > 0 管收尾：main 第 4 分钟末 freshCount 归零但队列还剩 1 个，去掉它多算一轮 → 5，
     20,000 组里恰好是全部 14,425 组正数用例各 +1，0 和 -1 的 5,575 组不受影响；
   grid = 2 管正确性不管终止：删掉它不会死循环，freshCount 冲到 -6 / -87 就退出并返回 -1；
   提前 return 0 和 minutes++ 前置都是实测等价（各 0 差异），别当成关键去"修"；
   20,000 组与"逐分钟全图扫描"参考 0 差异；八连通错 8,737 组、删 freshCount-- 错 14,425 组；
   空网格 grid[0].length 直接 AIOOBE（p200 有 length==0 挡一层，这份没有）；
   锯齿矩阵：第 0 行更长就崩，更短就静默漏列（{{2},{1,1}} 给 1，应为 2）；
   入参被就地改写：同一份网格连调两次给 4 然后 0；
   BFS 栈深恒为 1：蛇形 20,100 格 1 ms，同数据递归 DFS 在 9,870 格就爆栈；1000×1000 一百万格 19 ms，队列峰值只有 598。
```
