# LeetCode 23 合并 K 个升序链表（对，但"一个一个并"是 O(k²n)）

> 对应程序：[LeetCode23_MergeKSortedLists.java](./LeetCode23_MergeKSortedLists.java)
> `main` 合并 `1->4->5`、`1->3->4`、`2->6` 三条链，实测：
>
> ```
> 合并后：
> 1 -> 1 -> 2 -> 3 -> 4 -> 4 -> 5 -> 6
> ```

---

## 一、代码做的事

```java
ListNode mergedList = lists[0];
for (int i = 0; i < lists.length - 1; i++) {
    mergedList = merge(mergedList, lists[i + 1]);
}
```

第 1 轮把第 0、1 条并成一条；第 2 轮把这条"两条的并集"再和第 2 条并……第 k-1 轮并完，得到结果。`merge` 就是 21 题那份（`<` 相等取右边、剩余整段挂上）。

逻辑完全正确，问题在**合并顺序**。

## 二、复杂度：越并越长的那条链被反复扫描

设每条链长度 n、共 k 条。第 i 轮开始时，`mergedList` 已经有约 `i·n` 个节点，这一轮要把它**完整走一遍**，于是总代价：

```
n + 2n + 3n + ... + (k-1)n ≈ n·k²/2
```

总节点数是 `k·n`，所以相对于节点数是 `O(k·N)`。两两分治每轮把链表数量减半，每个节点只参与 `log k` 轮，是 `O(N log k)`。

## 三、实测：同一批节点，只换合并顺序

构造 k 条链表、每条 500 个节点、列间值交错（每轮都必须比较到底），固定同一份数据分别跑三种写法：

| k | 总节点 | 顺序两两合并（他的） | 两两分治 | 优先队列 |
| --- | --- | --- | --- | --- |
| 200 | 100,000 | 38 ms | 3 ms | 12 ms |
| 500 | 250,000 | 426 ms | 9 ms | 22 ms |
| 1,000 | 500,000 | 2,331 ms | 32 ms | 39 ms |
| 2,000 | 1,000,000 | **22,616 ms** | **199 ms** | 301 ms |

节点总数只翻了一倍（50 万 → 100 万），顺序合并的耗时翻了近 10 倍 —— 这就是 `k²` 项在起作用。k=2000 时和分治差 **114 倍**；在实际提交里，这个差距就是"超时"和"通过"。

优先队列慢于分治但仍远快于顺序：每个节点进出堆各一次，`O(N log k)`，常数比纯指针合并大。

## 四、正确性：随机对拍

k 在 1..10、每列 0..20 个节点、**允许整列为 null**，固定种子 20,000 组，与"全部摊平后排序"对比：

```
不一致 = 0
```

边界：

```
空数组 = null
null 数组 = null
全 null 元素 = null
单个链表是否原样返回 = true      ← 连头节点都没换
```

`lists[0]` 为 null 也不会崩：`merge(null, x)` 直接返回 x。这说明它挡住的是"空"，没挡住的是"慢"。

## 五、节点复用

k=3 时输出 8 个节点，全部来自三条输入链表（8/8）：

```
全部来自原链表 = true
```

`merge` 只改 `next`，所以合并后三条原始链都被拆开 —— 和 21 题一样，之后只能从返回的头访问。

## 六、一句话记住

```
   逻辑 = 21 题的 merge 套一个 for 循环，结果一定对；
   但"拿累加结果去并下一条"会把长链反复走一遍：O(k²n)；
   2000 条 × 500 个节点实测 22,616 ms，两两分治 199 ms（114 倍）；
   分治/优先队列都是让每个节点只参与 log k 轮；
   20,000 组随机（含 null 列）0 差异，空数组合法。
```
