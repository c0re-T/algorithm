# LeetCode 438 找到字符串中所有字母异位词（`> 0` 和 `>= 0` 这两个判断不是对称的）

> 对应程序：[LeetCode438_FindAllAnagramsInAString.java](./LeetCode438_FindAllAnagramsInAString.java)
> 定长滑动窗口 + 一张 26 格的频次表。`main` 用的是 LeetCode 那个会把排序法卡住的长串
> （`"eklpyqrbgjdwtcaxzsnifvhmou"` 重复 150 次，`p` 是其中 21 个字母），实测打印 150 个起点：
>
> ```
> [4, 30, 56, 82, 108, 134, ...]      ← 间隔恰好是 26（每个重复段里命中一次）
> ```

---

## 一、`need[]` 的语义在这 20 行里换了两次

```java
int[] need = new int[26];
for (char c : p.toCharArray()) need[c - 'a']++;     // 此刻 need[x] = "还欠 x 几个"

for (int right = 0; right < s.length(); right++) {
    char rightChar = s.charAt(right);
    if (need[rightChar - 'a'] > 0) matchCount++;    // ① 进窗口：还欠着才算数
    need[rightChar - 'a']--;                        //    欠额 -1（可能变负）
    if (right - left + 1 == p.length()) {
        if (matchCount == p.length()) result.add(left);
        char leftChar = s.charAt(left);
        if (need[leftChar - 'a'] >= 0) matchCount--; // ② 出窗口：不欠（含 0）才算它曾贡献过
        need[leftChar - 'a']++;                      //    欠额 +1
        left++;
    }
}
```

`need[x]` 中途可以是**负数**，含义变成"窗口里 x 多了几个"。正因为如此，① 和 ② 的判断符号不一样：

```
   ① 进窗口时：need > 0  → 这次进来的是「还欠着的」，才让匹配数 +1
   ② 出窗口时：need >= 0 → 走之前 need 是 0 或正，说明这个字符在窗口里没超额，它确实贡献过匹配数
                 need 已经是负数时，说明这个字符在窗口里本来就多出一个，它没贡献过匹配数，不该扣
```

**如果两处都写 `> 0`，②就会漏扣匹配数**，导致 `matchCount` 虚高、错报命中；都写 `>= 0` 则 ① 会多算。
这类"符号差一个"的地方，靠读代码很难看出来，只能拿对拍验。

## 二、和"每个窗口排序"那份对拍

固定种子 8,000 组随机（`s` 长度 1..40、`p` 长度 1..6，字母表只有 a/b/c/d，制造大量重叠）：

```
   滑动窗口版与排序版不同 —— 0 组
```

LeetCode 的经典例子也对得上：

```
   s = "cbaebabacd", p = "abc"  ->  [0, 6]      （两个实现都是 [0, 6]）
```

## 三、注释里那份"每个窗口排序"

```java
char[] sArr = sub.toCharArray();
Arrays.sort(sArr);
if (Arrays.equals(sArr, pArr)) result.add(i);
```

它是**正确的**（对拍 0 差异），慢在 `O(n · k log k)`。实测他 `main` 那种形态的长串：

```
   |s| = 100,000、|p| = 100：窗口版 2 ms，排序版 157 ms（约 78 倍）
   |s| = 3,000 、|p| = 20 ：窗口版 0 ms，排序版 1 ms
   他 main 里那串（|s| = 3,900、|p| = 21）：窗口版 1 ms，排序版 0 ms
```

第三行值得留意：**在他自己 `main` 的那个长度上，两种写法都看不出差别** —— 排序版的劣势要到 `|s| × |p|` 上去之后才现形（第二行 3,000×20 也还看不出来，第三行那个 100,000×100 才是"案例超时"的形状）。这跟马踏棋盘那篇里的结论一样：**规模不够大的复现，等于没复现。**

## 四、边界实测

```
   p 比 s 长   -> []          （第一行 s.length() < p.length() 挡了）
   p 是空串    -> []          （右-左+1 == 0 永远不成立，循环白跑一趟 s）
   s 是空串    -> []          （进不去循环）
   s 为 null   -> []          （挡了 null）
   含大写：findAnagrams("Abc", "a") -> ArrayIndexOutOfBoundsException: Index -32 out of bounds for length 26
```

最后一条是真会发生的：`'A' - 'a' = -32`，26 格数组直接越界。**题面保证只含小写字母**，所以交上去没事；
但这意味着这个方法**不能接受任何超出约定的输入**，而同一个思路换成 `Map<Character,Integer>`（像 p3 那样）就天然免疫 ——
这两份题解在"字符集假设"上的处理并不一致，值得当一条经验记：**用定长数组当哈希表，就等于把输入字符集写进了契约。**

另外注意 `need[]` 在方法结束时已经不是初始的欠额表了（一路加减）。这里没有复用所以无碍，
但如果以后把它改成"一个 Solution 对象连续调多次"，`need` 就必须每次重建（现在是每次调用 `new int[26]`，安全）。

## 五、和 49 题的关系：同一道题的两种"规范化"

`p49_groupanagrams` 用"排序后的串"当 key 把字符串分组；这一题用"26 个计数"当签名在定长窗口里匹配。
两者本质都是**给异位词类造一个唯一的代表值**：

| | 49 分组 | 438 找位置 |
| --- | --- | --- |
| 代表值 | 排序后的串（长度 = 词长） | 26 个计数（固定长度） |
| 代价 | 每个词 `O(k log k)` | 每个词 `O(k)` + 每次判断 `O(1)` |
| 窗口 | 无（整词分类） | 定长滑窗，`O(n)` 次判断 |

49 那题词长只有 100，排序无所谓；这题要在 10⁵ 长度上滑动，就必须换成计数 + 增量维护。
**"同一类等价关系，规模不同就得换实现"** —— 这两道题放一起看比单看一道更清楚。

## 六、代价：为什么必须是增量

窗口每右移一格，只有"进一个字符、出一个字符"两处变化，所以：

```
   匹配数 matchCount 用 ±1 增量维护        ← O(1) 一步
   而不重新数 26 个格子是否全部对齐         ← O(26) 一步
   更不重排整个窗口                        ← O(k log k) 一步
```

第三节那张表测的是"增量 vs 重排"这一档差距（157 ms vs 2 ms）；
"增量 vs 每次重数 26 格"这一档我没有单独测，`|s| = 10⁵` 下最多也就差 26 倍里的常数，
量级上远小于重排那档 —— 但这句只是估计，别当实测结论。

## 七、一句话记住

```
   进窗口判 need > 0、出窗口判 need >= 0 —— 这两个符号不不对称是因为 need 中途会变负（表示窗口里这个字符超额了），
   写成一个符号就会错报命中；8,000 组随机与"每窗排序"版 0 差异；
   定长数组把输入字符集写进了契约：'A'-'a' = -32 → AIOOBE，p3 用 Map 就免疫；
   注释那份排序版是对的，但在 |s|=100,000、|p|=100 上要 157 ms vs 2 ms，而在他 main 那个长度上两种都测不出差别；
   和 49 题是同一类等价关系的两种规模实现：词短用排序 key，串长用计数 + 增量维护。
```
